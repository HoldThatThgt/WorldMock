# LifeEnv 最终规格审计

> 状态：调研证据（历史依据，不构成当前规范）｜ 日期：2026-09-15 ｜ 结论：LifeEnv 已具备真实时间推进、活动区间结算、购买库存等主干能力，但本快照仍不能认定为完整满足设计规格；本文保留修复前发现及其证据身份。

> 历史审计快照：本文保留修复前发现及其证据身份，不描述当前实现状态。
> 后续修复、测试、突变审查与实际运行以 `docs/dev/implementation-status.md` 的对应提交收据为准。

## 审计结论

当前 LifeEnv 已经具备真实时间推进、活动区间结算、购买库存、独立工作验收和多人串行提交等主干能力，
但本快照仍不能认定为完整满足当时的规格快照 `docs/agentsociety2-design.md`（已退役，存于 Git 提交 `9b7fbc8`；现行规格见 `docs/dev/SPEC-life-runtime.md`）。工作产出尚未使用人物技能和工具效果，工作截止与身体阈值
未进入调度边界，重复内容没有改变效果，暂停活动不会在实验结束时形成截断终态。动作幂等重放还会返回过期的
`in_progress` 结果。这些问题会直接改变十二周足迹的行为与因果解释。

本报告只审计 LifeEnv，不读取凭据，不运行 Ray，也不修改被审计的引擎、活动、身体或规则代码。场景静态校验缺口
由同一任务后续仅在 `src/worldmock/life/scenario.py` 和 `tests/life/test_scenario.py` 修复，其余行为缺口交由父任务分派。

## 静态场景校验缺口

审计快照中的 `LifeScenario.model_validate` 接受以下无效输入：效率曲线输出 `2.0`、活动代谢当量 `-1.0`、任务地点
`missing-location`、任务雇主账户 `missing-employer-account`，以及重复 `route_id`。这些输入分别会造成无界效率、错误能量
模型、运行时查找失败、账户键错误或非唯一路由身份。

场景解析还没有约束技能和娱乐偏好的数值范围、商品要求地点引用、营业时间顺序、路线自然键唯一性、任务时间与场景窗口、
邮件任务引用以外的完整账户冲突，以及场景冻结的拒绝预算。后续修复必须只表达现有字段的闭集约束，不添加兼容层或新配置。

## 测试覆盖缺口

正式十二周场景只有套餐合同。多人场景虽然声明套餐、计时和计件合同各一个，当前 `tests/life/test_work_review.py` 仍只执行
正式场景首个套餐任务。没有测试通过真实引擎证明计时工资、计件验收、迟交、雇主资金不足、累计合同最大时长和同任务付款
幂等同时成立。

现有活动测试只截断 `ACTIVE` 活动，并未覆盖暂停活动在实验终点的行为。现有幂等测试把终态后的过期 `in_progress` 当成
正确结果。多人测试覆盖独立等待的提交顺序，没有构造共享库存或共享任务冲突。内容测试没有断言重复观看改变效果，也没有断言
内容条目自己的娱乐参数实际参与结算。

## 修复验收案例

| 行为 | 必须通过的正反例 |
| --- | --- |
| 工作效率 | 相同时间与睡眠下，技能不同产生不同有效工作量；明确生效的工作工具按冻结规则改变产出；计时工资仍只按合格实际时长计费 |
| 调度边界 | 工作截止和身体阈值早于活动反馈时，`scheduling_state` 返回更早边界并在该时刻形成可观察结果；所有边界严格晚于当前时刻 |
| 活动终态 | 活动、暂停活动和恢复后的活动在实验结束都形成唯一截断终态；已结算区间不重复计入 |
| 动作幂等 | 活动完成、取消、失败或截断后，重放同一请求返回对应最新终态；更换参数继续触发协议错误且不重复副作用 |
| 工作合同 | 多段工作累计不能超过合同最大时长；套餐、计时、计件、迟交、返工、雇主资金不足和重复提交都有真实结果与账本守恒 |
| 内容重复 | 首次、续看和重复观看分别记录真实区间；内容条目参数、人物偏好与重复规则共同形成可解释效果 |
| 多人冲突 | 两人对最后一件库存和同一不可逆任务以反转到达顺序提交，结果只由已记录的冻结顺序决定；相同种子重演得到相同顺序 |
| 场景校验 | 正式场景和多人场景成功载入；每一类非法曲线、代谢、技能、地点、账户、路线、任务与拒绝预算都在启动前失败 |

## 验证方法与限制

审计使用源码逐行控制流检查、场景字段统计、已有测试意图检查和隔离的 Python 运行探针。探针只在临时目录建立状态，
没有调用外部模型或网络。场景统计结果为：正式场景一人、五十六个套餐合同；多人场景两人，三种合同各一个。

本阶段没有运行 Ray、全量门禁或 Uncle Bob mutation review。当前工作区在首次审计时全部文件尚未纳入 Git，因此无法给出可靠的
基线提交或标准 diff 身份。父任务建立干净 Git 基线并整合行为修复后，需要对上述反例进行一次独立 mutation review；绿色测试只有
在对应行为破坏会被测试杀死时才能作为规格闭环证据。
