## 0. 采用的解释，以及与五份测量的差异

**字的口径。** 「字」就是 Python `len()` 数出的字符数，汉字、数字、字母、标点各算 1，这也是提案现在用的单位。各级上限如下：

| 级别 | 上限 | 计数范围 |
|---|---|---|
| 今天条目 | ≤120 字 | 只数「核验」和「自述」各字符串的长度，键名、引号、`时刻`、`类别` 不算 |
| 日回顾 | ≤200 字 | 每类的 `text` |
| 月回顾 | ≤800 字 | 每类的 `text` |
| 年回顾 | ≤2000 字 | 每类的 `text` |

**10k token 额度。** 按 tokens 测量，新记忆层的中心值是 **0.638 token/字**（一阶差分拟合，bootstrap 95% 区间 0.630–0.645）。10k token 约合 15,670 字，因此硬预算定为 **14,000 字**：按整个渲染后的记忆层 `len` 计，含键名。这相当于中心值 8.9k token，按 0.67 算 9.4k，按 0.70 算 9.8k。

**与五份测量的差异：**

1. **token 换算。** entries 测量（0.593，预算 16,500）和 econ 测量（0.60，预算 16,400）用的都是现行记忆层的字符构成。现行层里约 12% 是英文键名字母，每个只合约 0.06 token。新层的键名是中文，几乎没有字母，所以这两个数不适用。views 测量的 0.75 只是看法正文（91% 是汉字，模型带截距）的比率；回顾正文实测是 0.657。
2. **report_status 条目的前缀。** 用「进展·〈短名〉：」。entries 写的是「〈短名〉进行中：」，两者长度相同；新写法与「看法·」同属一类，便于 `noted_label` 扫描。
3. **被拒行。** 写成「被拒：〈动作〉〈对象〉」，不带原因。这采用 code 测量的写法，而不是 entries 那种按 error_code 映射的中文原因。原因仍在进度层 `rejected_today` 的 `why` 里，免去一张映射表。V 的示例因此每条短 13 字。
4. **短名。** 不加「（第N次）」。code 测量建议按先到先得给标签，这里改为直接用冻结的活动名去掉后缀；同一条目内有两项同名时，沿用现行 `_labels` 的做法（memory_layer.py:299-303）保留全名；`noted_label` 把一个标签映射到当天所有同名活动。这样做同样只追加、可复现。
5. **看法移出的阶段。** 放在 P2（views 测量），不放 P1（code 测量）。code 担心的重复，靠「P1 的今天条目不渲染看法」来解决。列为第 29 条。
6. **兜底回落目标。** 回落到 12,000 字（entries 测量），不回落到 econ 的 75%。
7. **今天的时刻段检索。** entries 测量的建议，列为新的第 28 条。
8. **个人事务变更句。** 照请求的闭集取值（requests.py:262：新增、更新、取消），写成「新增个人事务「X」」等，不用 entries 的「记下待办」。

- **`类别`**：主请求的类别。主请求是本次决策的第一个世界请求；开始组取槽位 1 那一项。条目里如果还有别的类别的行或项，按首次出现的顺序用「、」接在后面，例如「工作、饮食」。V 有 37/406 条是混合类别，B 36/409 条。
- 宿主内部另外保存：日期、`decision_id`、来源事件身份、每一行和每一项各自的类别、条目全文（见第 7 点），以及 routine 记忆。这些都不渲染。

**2. 窗口。**
- 记 C_j 为第 j 次决策提交的末事件序号：取它第一条世界请求结果所在那次提交的末序号，用 `store.commit_last_seq`（recording_engine/storage/store.py:357-373）。C_j 提交后不再变化，缓存在 `_AgentEvents.lowers` 旁边（memory_layer.py:51-61）。
- 记 B_D 为零点界：本地零点之前最后一个事件的序号，取法与 `rejected_today` 相同（progress_layer.py:321-322）。
- 第 k 条的窗口是序号落在 (max(C_{k-1}, B_D), C_k] 的事件。它包括本次决策之前时钟推进时结算的自然结束、送达和付款，也包括本次决策自己的提交。

**25. 往日看法的原文要不要单独可查。**
- 选项 A：不另存，过了零点只在回顾里。
- 选项 B：另建一份带日期、去重、只供检索的看法列表。
- **推荐 A。** 理由：
  - B 违背「往日只以段落出现」；
  - 它只能按关键词查到，而提示里没有线索（V 5 天只查了 2 次）；
  - 只留最新一条，会掩盖看法的变化；
  - 会原样保留过时或编造的看法，例如「自己做的番茄炒蛋配清炒青菜」到 10-12 还在被复述；
  - 同一条看法会有第三份副本。
- 代价：日回顾只保留约 10–25% 的看法文字。用 M10「看法对象覆盖率」和 M12 跟踪，结果不合意时再重议。

**26. report_status 条目写什么。**
- 选项 A：「进展·〈短名〉：」按规则 B 写进自述，进度层不再保留。
- 选项 B：A 的基础上，播报条目单独限 60 字。V 每天少 1.0–1.6k 字。
- 选项 C：只写核验「播报〈短名〉」，总结只进全文。
- **推荐 A。** 都远在预算以内；进展是收尾之前，模型能看到的自己唯一的中途记录。

**27. 120 字以内的取舍顺序。**
- 选项 A：规则 B，先给每条开头。
- 选项 B：严格按优先级依次放满。V 76 条看法里 0 条完整、64 条看不到；非 routine 记忆 22 条全看不到。
- 选项 C：看法紧跟核验。带看法的收尾里，看法整条放得下 62/75 条（B 42/55），总结只拿剩下的位置。
- **推荐 A。** 总结和看法都能留下开头；几种规则的总大小只差 0.1–1%。

**28. 「今天」检索加时刻段。**
- 选项 A：加「今天 HH:MM」和「今天 HH:MM~HH:MM」。
- 选项 B：只靠关键词。
- **推荐 A。** 一天的全文有 12.1–17.0k 字，超过 6,400 字的上限；截断的条目又散在一天各处。工具指纹只在 P1 变一次。

**29. 看法移出人设层放在哪一期。**
- 选项 A：P2，与层序调整同期。
- 选项 B：P1，与按决策的条目同期。
- **推荐 A。** 理由：
  - P1 试点的 M1、M4 读的是饮食多样性，而 3 次刀削面午饭里有 2 次是看法带动的，P1 就移出会把两种效果混在一起；
  - P2 的层序调整需要逐字节不变的人设层；
  - P1 的条目不渲染看法，就不会重复。
- 代价：P1 期间每个决策多约 1k token，约 $0.018/天；P1 的规则文字多 4 处临时写法。
