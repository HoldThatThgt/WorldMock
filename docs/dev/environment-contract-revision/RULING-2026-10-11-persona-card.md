# 裁决记录：人物卡片由数据集直接填写

> 日期：2026-10-11。规格冻结之后由所有者作出，随集成分支 `feat/environment-contract-revision` 一起合入。
> 本记录只写这一条裁决，以及集成时按它补上的三件事（见「集成时定下的三件事」）。冻结的[规格](SPEC-environment-contract-revision.md)和[提案](PROPOSAL-environment-contract-revision.md)不回写；
> 两者与本记录不一致的地方以本记录为准。
> 证据层级：读代码和离线套件。没有调用模型，没有做过真实运行。

<a name="ruling-persona-card-所有者的原话"></a>
## 所有者的原话

所有者看到「声明的作息与模型读出的时间冲突时保留卡片值并警告」「成对关系六条」这一套之后说：

> 唉 搞这么复杂干嘛 不要给数据集兜底，把检查去掉吧；系统实际要使用的字段改成必填，也不要什么模型去读故事

被告知今天是模型把 `background_story` 读三遍来填人物卡片之后说：

> 这不就是脱裤子放屁吗，你直接把这个表的格式拿出来让数据集填不就完了吗

<a name="ruling-persona-card-规格和提案原来怎么写"></a>
## 规格和提案原来怎么写

规格「人设作息窗口」一章、「版本、身份与基线」里人物卡片的几行，以及「实施顺序与验收」里身体与作息阶段讲作息的部分，原来的安排是：

| 事项 | 原来的写法 |
| --- | --- |
| 卡片从哪来 | 运行开始时模型读 `background_story` 三次，逐字段取共识；没读到的时间用引擎自带的缺省值补上 |
| 社交需要增长 | 模型给人物打大五分数，外向性换算成每小时增长 |
| 作者写的作息 | 七项可选；写了就原样盖进卡片，盖不进去时保留模型读出的值并记 `CARD_FIELD_CONFLICT` |
| 加载检查 | 时段要在 0 到 24（就寝到 30）之内、跨度不超过 12 小时；六条成对关系；卡片再检查时间先后 |
| 给作者的工具 | `worldmock profile compile`、`check`、`validate` 三个命令，用来看模型读出了什么、覆盖了多少 |
| 版本 | `persona.toml` 的 `schema_version` 保持 1，编译产物结构号升到 5 |

<a name="ruling-persona-card-现在适用什么"></a>
## 现在适用什么

| 事项 | 现在的做法 |
| --- | --- |
| 卡片从哪来 | 数据集作者在 `persona.toml` 里按表直接填：身份、当前处境、关系、习惯、口味、应对方式、作息。引擎逐字段照搬，不调用模型，不补缺省值，不改写任何数 |
| 社交需要增长 | 作者直接填 `social_need_growth_per_hour`，0.02 到 0.10；大五分数整个删除 |
| 必填 | 系统实际要用的字段都必填：睡眠中点、每日睡眠需要、起床、出门、午饭、晚饭、就寝五个时段、社交需要增长、身份、当前处境、关系、习惯、口味、应对方式。下班、到家两个时段可以不写，不写就是没有固定时刻，与工作安排没有任何联动 |
| 检查 | 只留表的格式和计算要用的：类型、必填、公式需要的数值范围、提示预算依赖的条数和字数上限、卡片文本的 600 汉字上限；每个时段只要求是两个有限数且起点小于终点 |
| 删掉的检查 | 六条成对关系、0 到 24 与 30 小时上界、12 小时跨度、越过午夜的平移、卡片的时间先后、下班到家的先后、取整。`[5.0, 7.0]` 的就寝、早于晚饭的就寝、写成 25 点以后的下班都能加载，人物看到的就是作者写的时刻 |
| 删掉的东西 | 读故事的三次抽取与共识、缺省补齐、大五与映射表、声明覆盖与两个 `CARD_FIELD_` 警告、覆盖率报告、编译产物及其结构号和提示版本、三个 `worldmock profile` 命令、运行开始时为人物发的模型请求、`[model]` 里只给抽取用的 `persona_validation_max_retries` |
| `background_story` | 仍是必填的文字，零点计划照旧原样读它；只为抽取服务的一百字符下限删除 |
| 恢复 | 只留一条核对：恢复出来的卡片必须等于用冻结的 `persona.toml` 重新构造出的卡片 |
| 版本 | `persona.toml` 的 `schema_version` 升到 2，写 1 的文件被直接拒绝，没有读取旧格式的分支。人物工作区里的结构化卡片形状不变，所以 `AGENT.json` 的结构号不变。运行清单、质量报告和 `config.toml` 的结构号各升一次，见「集成时定下的三件事」 |

各处读到同一个值：人设层、卡片文本、零点计划、身体（饭点、困意、欠觉、社交需要增长）和评估（下班、到家偏离）读的都是 `persona.toml` 里的数。
原来「声明和模型读出的时间冲突」这个唯一例外随模型抽取一起消失。

<a name="ruling-persona-card-写这条裁决时定下的细节"></a>
## 写这条裁决时定下的细节

裁决没有写到、实现必须定下的点：

| 事项 | 定下的做法 |
| --- | --- |
| 饭点对身体的作用 | 钟面时刻落在午饭或晚饭时段里时饥饿体感加 0.15。时段按钟面读，写成 25 到 26 的午饭就是 01:00 到 02:00；这个算法对任何「两个有限数、起点小于终点」的时段都算得出来，所以饭点时段原来的 0 到 24 检查和「午饭晚饭不重叠」检查一并删除，重叠时也只加一次 |
| 联系渠道 | 每个关系写一到三项非空白文字，用词不限。实现分支曾把抽取提示里的「电话」「微信」「见面」做成加载时检查的闭集，集成时去掉，见「集成时定下的三件事」 |
| 没有关系或习惯的人物 | `relationships`、`habits` 必须写出来，可以是空数组 |
| 口味里重复的词 | 原样保留，不再替作者去重 |
| 给作者的拒绝原因 | 每条都先写出错的字段，例如 `identity.age is required`、`lunch_window: must be two finite hours with start < end`；缺了哪个必填字段一看就知道。路径只由字段名、表的键和数组下标组成，日期例外里的班次写成 `work_schedule.exceptions.2026-01-05` |
| 卡片文本的 600 汉字上限 | 条数和字数上限各管一个字段，合起来仍可能超过 600 汉字，所以加载人设表时就把卡片文本构造一次并数汉字，超出以 `PERSONA_INVALID` 拒绝并写出汉字数。`worldmock validate` 通过的表不会在运行开始时因为卡片太长而失败 |
| 运行输入警告 | 警告机制保留，因为还有两种与卡片编译无关的警告：没有任何 app 绑定内容而人物写了媒体口味，地点显示名带坐标或标识。随抽取和覆盖率删除的四种警告码一并从闭集里去掉，质量报告里按警告码计数的键集随之变化 |
| 运行清单 | 少了 `world_dynamics` 一项（它原来保存由大五换算出的社交需要增长），这个值现在在冻结的 `persona.toml` 里；`stage_model_identity` 少了 `persona_validation_max_retries` 一个键。顶层字段集合变了，结构号随之升一次 |
| 评估读什么 | 下班、到家窗口直接读 `persona.toml`，不再从人物工作区取卡片。窗口和人设层一样按钟面读，一次离开或到家与离它最近的那一次窗口比较：下班写成 `[25.0, 25.5]` 的人物凌晨 01:10 离开算准时，前一晚 23:50 离开算早 70 分钟 |
| 引擎包里的数据目录 | `persona-mapping.toml` 删除后，`src/worldmock/data/` 只剩包声明，里面没有任何规则文件。实现分支把这个空包留着，集成时连同 `pyproject.toml` 里给它的 `package-data` 一节和代码身份里读它的分支一起删除，见「集成时定下的三件事」 |
| 夹具人物 | 测试夹具的 `persona.toml` 写成完整的表，取值就是此前离线测试手工准备的那张卡片，人设层和以前一样；午饭、晚饭、就寝现在必填，所以夹具人物从此有饭点加成，零点计划里也多出这三个时段 |

<a name="ruling-persona-card-对基线的影响"></a>
## 对基线的影响

夹具的 `persona.toml` 改了，`persona_sha256` 随之变化；夹具的 `config.toml` 把 `schema_version` 从 1 改成 2，`config_sha256` 也随之变化。
规格「版本、身份与基线」里写的「`persona_sha256` 不变」「`config_sha256` 不变」都不再成立；`seed`、`map_sha256` 和 `environment_id` 仍然不变。
两份完整日基线和录制样例 `viewer-context.json` 仍只在修订末尾重做一次，本裁决的改动不单独重冻。
规格「核对升号次数」里「人物卡片 4 变 5」一项改为：编译产物的结构号随编译产物一起删除，`persona.toml` 的 `schema_version` 1 变 2；
「运行清单结构号、质量报告结构号没有变」一项改为：运行清单 5 变 6、质量报告 7 变 8、`config.toml` 的 `schema_version` 1 变 2，各恰好一次。

<a name="ruling-persona-card-集成时定下的三件事"></a>
## 集成时定下的三件事

实现分支合入集成分支时，集成者按规格的「升号原则」和所有者「不给数据集兜底」的原则补了三处。
每一处都先改设计正文，再改实现和测试，与合并在同一组提交里。

**三个结构号各升一次。** 规格的升号原则是：一个结构号只守一种结构，字段集合、取值闭集或可接受的取值域变了就升号，各升一次。
这条裁决让下面三种结构的字段集合或闭集变了，实现分支没有动它们的结构号：

| 结构 | 变了什么 | 旧值 | 新值 | 旧值在哪里被拒绝 |
| --- | --- | --- | --- | --- |
| 运行清单 | 顶层少了 `world_dynamics`，`stage_model_identity` 少了 `persona_validation_max_retries` | 5 | 6 | 打开、恢复与重放报 `Runtime environment identity mismatch`；导出认证报 `Export frozen run manifest or environment identity is invalid` |
| 质量报告 | `input_warnings.code_counts` 的键从六个警告码变成两个 | 7 | 8 | 导出认证按事件重算整份报告，报 `Export quality report disagrees with authoritative events` |
| `config.toml` | `[model]` 少了 `persona_validation_max_retries` | 1 | 2 | 加载时以 `RUN_CONFIG_INVALID` 拒绝，原因 `schema_version: Input should be 2` |

规格「版本号与结构号」表里这三行写的「不变」因此作废。数据集作者要把 `config.toml` 第一行改成 `schema_version = 2`，
并删掉 `[model]` 里的 `persona_validation_max_retries`。修订前的运行本来就因为规则版本、世界状态结构和代码身份不能恢复或重放，
升号之后它的清单和质量报告自己也标明不是当前结构，不需要靠别的身份间接拒绝。

**联系渠道不设闭集。** 「电话」「微信」「见面」三个词原来只存在于已删除的抽取提示里，引擎的任何计算都不读渠道的取值，
人设层和卡片文本只是把它照写出来。把它做成加载检查的闭集是在替数据集把关，与所有者的原则相反，所以去掉：
`relationships[].channels` 的每一项只要求是非空白文字，重复的词原样保留。条数仍是一到三项：
卡片文本把关系写成「渠道、渠道联系」，没有渠道这句话写不出来，所以至少一项；至多三项是提示容量依赖的条数上限。
渠道写得很长时由卡片文本的 600 汉字上限在加载时拒绝，不另设单项字数上限。

**删除只剩包声明的数据目录。** `src/worldmock/data/` 随 `persona-mapping.toml` 的删除成了空包，一并删除的还有
`pyproject.toml` 里的 `[tool.setuptools.package-data]` 一节和代码身份里读这个目录的分支。
规格写的「本次修订不改 `pyproject.toml`」在这一点上作废：`pyproject.toml` 相对修订前只少了这一节，
没有任何依赖变化，`uv.lock` 与 `requirements/` 逐字节不变。代码身份覆盖的范围回到规格「指纹与派生身份」写的那样：
`src/` 与 `custom/` 的全部 Python 源码、`pyproject.toml`、`uv.lock` 和实际导入的 AS2 包。
