## 为什么现在做

- **修改集中在最大的文件上。** `life/` 占 `src` 的 56%（96 个模块、28,540 行）。基线之前的 523 次提交里，`engine.py` 被改了 61 次，`custom/agents/life_agent.py` 53 次，`life/models.py` 48 次。
- **改一处要动很多处。** 改一处行为，要同步规格、合同、设计章节与汇编 HTML、验收台账与突变登记；文档里的 1,916 处行号引用大多已经过期（第二节）。
- **反馈太慢。** 全量测试在 6 个进程上要一个多小时（第三节）。
- **`engine.py` 快到上限了。** 它已有 1,904 行，离风格门禁的单文件上限 2,000 行只剩 96 行。

这些都不是单点缺陷，而是规模上去之后每次改动都要付的固定成本。本文的改动都不改变行为，目的是降低之后每次改动的成本。

## 一、分层：让依赖只朝一个方向

### 现状

1. **模块级导入已经无环。** 不计函数内导入与 `TYPE_CHECKING` 块，`life/` 的 96 个模块按最长依赖链排成 20 层：最底层是 `readable`、`sleep`、`felt`、`social` 等不依赖其他 life 模块的纯函数模块，最顶层是依赖 62 个模块的 `engine`。唯一的模块级互相导入是 `admission` 与 `activity_control`，而 `activity_control` 一侧写在 `TYPE_CHECKING` 块里，只服务类型标注，运行期不成环。
2. **环藏在函数内导入里。** `src/worldmock` 共有 115 处函数内导入。其中 16 处的目标模块在模块级已经直接或间接依赖导入方（`life/` 14 处、`footprints/` 2 处），另外 `runtime` 与 `validation` 两个模块在函数内互相导入（共 7 处）。把这些边算进去，77 个模块（26,429 行：`life/` 的 73 个模块，加上 `runtime`、`validation` 和 `scheduling` 的两个模块）彼此可达：其中任何一个的改动，都可能在运行期牵动其余 76 个。`footprints/` 另有两个小环（3 个与 2 个模块）。函数内导入只是让环在导入时不报错，依赖本身仍在。
3. **回边集中在少数几种原因。** 下表 7 类共 17 处（`runtime` 与 `validation` 的互相导入记 1 处）。大多数是底层模块需要的一个常量、类型或小函数放在了上层模块里，修法是把定义往下移，而不是改逻辑。其余 99 处函数内导入不成环，可以直接提到模块顶部；已验证把它们同时上提不会产生新环。
4. **`LifeEngine` 是一个分在四个文件里的类。** `engine.py` 里的类本身有 76 个方法、1,418 行，另由 `ObservationMixin`（`observe.py`，42 个方法、579 行）、`SessionActionMixin`（`session_actions.py`，53 个方法、747 行）与 `StorefrontRuntimeMixin` 拼成。两个大 Mixin 分别使用 43 个和 52 个引擎私有属性或方法，状态全部经 `self` 共享：拆了文件，没有拆开依赖。`engine.py` 是全仓修改最频繁的文件（基线前 523 次提交中改动 61 次）。
5. **测试直接依赖引擎内部。** 45 个测试文件里有 148 处访问引擎私有成员，最多的是 `_observation_data`（32 处）、`_layer_context`（16）、`_work_reviewer`（13）、`_place_names`（9）、`_round`（8）；另有 39 处 monkeypatch 私有名字。215 个测试文件导入 `life` 模块。

### 方案

**1.1 守卫先行。** 新增 `tests/test_import_graph.py`：纯 `ast` 实现，不引入新依赖，与 `tests/test_style_gate.py` 同一做法。四条规则：

- 规则 1：`src/worldmock` 与 `custom/` 的完整导入图（模块级加函数内导入，不含 `TYPE_CHECKING` 块）无环。
- 规则 2：函数内导入只允许出现在登记表里，每条写明模块、被导入名与理由；理由只有两类：命令行入口为启动速度延迟导入，以及可选的重依赖（如 AS2）。其余一律写在模块顶部。
- 规则 3：`life.models` 和它在模块级依赖的模块组成基础层；基础层只导入基础层与 `worldmock.errors` 等全局底层模块。
- 规则 4：生产代码里只有门面的使用者 `custom/envs/life_env.py` 导入 `life.engine`（测试除外）。`observe` 与 `rhythm` 目前的两处导入就是 1.2 要去掉的回边。

守卫上线时，现有 17 处回边全部写进「已知违例」表；之后每修一组就从表里删掉，表只减不增。这样守卫第一天就能挡住新增的回边，不必等全部修完。

不推荐引入 import-linter：要在 `pyproject.toml` 加新的开发依赖（还会改动计入运行身份的 `uv.lock`），而且门禁要在没有 `uv` 的机器上也能一致运行（见[共享规则单一归宿与可重建环境提案](PROPOSAL_2026-10-04_SHARED_RULES_AND_REBUILDABLE_ENV.md)）；上述四条规则用 `ast` 实现约一百行，并且可以给出带中文说明的失败信息。

**1.2 按上表分 7 组去掉回边。** 每组一个小提交，只移动定义、更新导入。旧位置保留一个同名再导出，过一个版本周期再删，以免文档引用与测试导入一次改太多。

**1.3 上提其余函数内导入。** 回边清零后，把其余 99 处函数内导入提到模块顶部（登记表允许的入口延迟导入除外），依赖在文件头一眼可见，层次由守卫保证。

**1.4 拆开 `LifeEngine`。** 在 1.1–1.3 完成之后进行，分三步：

1. 先给测试开公开接缝：为上面五个最常被测试访问的私有成员提供只读的公开方法或测试辅助函数，测试改用接缝。这一步不动生产结构，之后的搬移不会再牵动 45 个测试文件。
2. 引入显式上下文 `EngineContext`（世界状态读写、场景、语义、足迹存储与运行设置），把三个 Mixin 改成接收上下文的协作对象：`ObservationBuilder`（原 `observe`）、`ActionHandlers`（原 `session_actions`）、`StorefrontRuntime`（原 `storefront_runtime`）。
3. 从 `engine.py` 按方法簇拆出协作对象：决策轮次（开始、提交、排队、分派、结算、提交与撤销，以及同刻记账，约 370 行）；时间推进（`advance`、活动推进、预排事件与下一时刻，约 250 行）；工作验收协调（约 150 行）；模型往来与记忆证据登记（约 150 行）；反事实干预（约 55 行）；社交投递并入 `social_actions`（约 120 行）。`LifeEngine` 保留为门面，供 `LifeEnv` 调用的公开方法签名不变。

预期 `engine.py` 从 1,904 行降到 500 行左右。这是搬移不是删减，总行数基本不变，但每个模块的扇出与修改热点都会变小。

**不做：** 不按活动种类建处理器类。前次调研估计这会净增 100–300 行，而且与 `admission.group_refusal` 冲突：该函数对一个请求里的全部条目逐条检查准入，报第一条不成立的原因，结果与条目先后无关；按种类拆开后，这个顺序就无法保证。

### 风险与约束

- **突变锚点与文档行号：** 这几个文件上登记了验收突变，现行文档也有大量行号引用（数字见第二节）。搬移代码要么同步改登记与文档，要么先落实第二节的符号引用与符号作用域锚点。建议先做第二节的 2.1 与 2.3，再做 1.4。
- **运行身份：** 任何源码改动都会改变 `code_sha256`，已有检查点不能续跑。应选在没有进行中的长运行时合入。
- **持久数据：** 全仓未用 pickle，也不保存 Python 类路径；事件与检查点是 SQLite 中的 JSON。搬移类不影响旧数据的读取。
- **行为不变的证据：** 现有测试没有逐字节比较导出。建议在 `tests/integration/test_dayrun_complete_days.py` 的完整双人自然日（脚本化模型、真实人物循环、含检查点恢复）上加一份基线摘要：事件序列与导出文件去掉运行身份字段（`code_sha256`、运行编号等）之后的 sha256。重构期间每一步都比对；有意改变行为的提交单独更新摘要并写明理由。

### 验收

- `tests/test_import_graph.py` 通过，「已知违例」表为空，函数内导入登记表只剩入口延迟导入。
- 全量测试通过；完整自然日的导出摘要与基线一致。
- `engine.py` 不超过约 600 行；`life.models` 的全部依赖（含函数内）都在基础层。

## 二、让文档与测试不再钉住源码文本

### 现状

1. **行号引用大多已经过期，门禁不检查。** 文档里共有 1,916 处 `文件.py:行号` 引用，分布在 41 份文档。按 INDEX 状态列区分，现行文档只有 7 份含行号，共 348 处，其中 343 处在 SPEC 文件里；`CONTRACTS.md`、`design/`、`manual/`、`VERIFICATION.md`、INDEX、`ARCHITECTURE.md` 与 README 一处都没有。其余 1,568 处在 34 份历史性文档里（实施台账、验收记录、调研与提案）。
   - 对引用旁边写了符号名的那部分做机械核对：在所引行号前后 5 行内能找到该符号定义的，现行文档只有 27%，历史文档只有 34%；被引用的行在引用写下之后已经移动或改动的，分别占 92% 与 89%。五份在文件头声明了「行号取 `<提交号>`」的文档，在其基线提交上 96% 仍然对得上。可见问题不是当时写错，而是没有固定基线的行号必然过期。
   - `scripts/documentation_gate.py` 只检查反引号里以 `docs/` 开头的 `.md` 路径是否存在；`.py` 路径、行号与 Markdown 链接都不判定，它的测试还明确断言忽略 `engine.py` 一类引用。
   - 文档里已有 506 处 `路径.py::名字` 形式的符号引用，其中 80 处（16%）解析不到。符号引用的写法已经在用，只是没有门禁。
2. **代码与测试也按章节名引用规格。** `src` 与 `custom` 的 docstring 引用 `docs/dev/SPEC-*.md` 共 617 处，测试 572 处，最多的是一日运行保真（150 处）、人物 Prompt（110）、个人事务（101）、life-runtime（100）与时间和能量（98）规格。规格一旦合并或改名，这些引用都会失效，而目前没有任何检查。
3. **突变锚点绑在文件上。** 147 条验收突变（个人事务 101 条、工具交互 46 条）分布在 53 个生产文件。`tests/mutation_runner.py` 的 `mutated_source` 要求 `original` 在整个文件里恰好出现一次；注入方式是在子进程里为该模块名装入内存加载器，不写文件。第一节准备拆分的文件上有 16 条，落在 11 个符号上（`models` 6 条，`engine` 5 条，`runtime._build_society` 3 条，`observe` 与 `session_actions` 各 1 条）。每条 `original` 在它所在的最内层函数、类或赋值里都是唯一的。
4. **一部分测试钉住与行为无关的源码文字。** 31 个测试函数读取生产源码：18 个是规则门禁（风格、错误合同等，属于正当用途），4 个是 AST 结构检查，9 个是与行为无关的文本钉，共登记 189 行。最大的一组在 `tests/time_and_energy_acceptance.py`：`REQUIRED_SYMBOLS` 有 157 条正则、225 个「正则 × 路径」组合（125 个指向生产文件，88 个指向文档）；`REMOVED_SYMBOLS` 有 97 条、132 个组合，要求某段文字在某个文件里不存在，文字挪到别的文件时会静默通过。代价已经出现过：`fd93aab` 的行为中性重构删掉了一个冗余表达式，随后 `350587d` 又把它加回来，只为满足钉点。另外，`tests/test_style_gate.py` 的单文件上限是 2,000 行，`engine.py` 已有 1,904 行，第一节的拆分因此有时限。
5. **文档文字被测试逐字比对，其中一部分是副本。** 17 个测试文件里的 34 个测试函数加 2 个门禁脚本，按 38 个写死的标题读取 37 处文档章节。
   - 正当的一类：把 `CONTRACTS.md` 里的系统层、反思提示、零点计划模板、工具说明与禁止渲染键，同模型实际收到的常量逐字比对。文档就是合同，比对保证两者一致。
   - 脆弱的一类：冻结增量规格里同一段文字的第二份副本（人物 Prompt 规格的系统层，个人事务规格 1.1、3.1、3.3、4.6、5.6 与 6.3）；从五份规格的散文里解析出的验收台账与裁决表；个人事务的 53 条突变句要求逐字拼回规格里的一段话；另有 110 个针对文档的正则。
6. **规格按修订叠加。** 18 份 SPEC 共 10,364 行，「冻结条款修订」出现 318 次。九份基础规格各被 5 份后续规格修订。修订最多的几条：一日运行保真 → `CONTRACTS.md`（21 行），个人事务 → 时间与能量（15），个人事务 → `CONTRACTS.md`（15），人物 Prompt → 时间与能量（15）。要弄清某条行为的现状，得按修订顺序读几份文档；INDEX 已写明 `CONTRACTS.md` 与 `design/` 描述现行实现。另有一处小的不一致：INDEX 的文档地图有一行状态是「归档」，状态词表里却没有这个词。

### 方案

**2.1 现行文档用符号引用，由门禁核对。**

- 写法是 `src/worldmock/life/engine.py::LifeEngine.advance`。嵌套名用点号连写；引用指向定义处，再导出不算定义。
- 扩展 `scripts/documentation_gate.py`：按 INDEX 状态列判定哪些是现行文档；现行文档里出现 `.py:数字` 即失败；`路径::限定名` 用 `ast` 解析，解析不到即失败。按样例实现，今天会报出 78 处。
- 历史文档保留行号，但文件头必须写「代码基线：<完整提交号>」。门禁只核对该提交存在，不拿 HEAD 比对。不再接受「提交号加未提交工作树」这种不可复现的基线（个人事务规格与其实施计划的文件头目前就是这样）。
- 状态词表补上「归档」。

**2.2 代码与测试对文档的引用改用稳定的章节标识，并纳入门禁。** 在会被引用的章节标题后加稳定标识（例如 `{#errands-2.3}`）。代码与测试引用 `SPEC-errands-workday.md#errands-2.3` 这样的标识而不是章节名。合并或改名时，标识随正文迁移；门禁检查 `src`、`custom` 与 `tests` 中的每个文档引用都能解析到现存的标识。这一步是 2.5 的前提。

**2.3 突变锚点改为符号作用域。**

- `SourceMutation` 用 `symbol`（`模块::限定名`）取代 `source` 路径；`original` 只要求在该符号的源码段里恰好出现一次；文件路径由模块名推出（登记里已有模块名到路径的映射）。
- 加一张 `RELOCATED` 表（旧 `模块::名` → 新 `模块::名`），代码搬家时只改这张表，门禁检查表里每一项都能解析。
- 原型对全部 147 条生成的变异源码与现行做法逐字节相同。迁移是一个改写两份登记文件的脚本加一次确认运行，约 0.5–1 天。应在第一节 1.4 拆 `LifeEngine` 之前完成。

**2.4 文本钉改为行为或结构检查。**

- `REQUIRED_SYMBOLS` 与 `REMOVED_SYMBOLS` 中指向生产代码的组合逐条判断：已有行为测试覆盖的直接删掉；确需保证存在的接口改为导入断言（例如 `from worldmock.life.day_planning import PlanDayClient`）或 `ast` 检查（例如「某常量的值是 3」）；「必须不存在」改为在整个包里检查，不再只查某一个文件。
- 指向文档的组合按 2.5 处理。
- `type(agent).__module__` 与写死 `__file__` 的检查改为检查类型或行为本身。

**2.5 已验收特性的规格合并后归档。**

- 规则：一个特性的验收记录登记之后，把它的「冻结条款修订」并入被修订文档的正文（或 `CONTRACTS.md`、`design/`），并在被修订文档的版本表记一行。增量规格、实施计划与验收记录改为「归档」状态，移到 `docs/archive/<特性>/`。
- 归档之前先把测试读取的内容移出增量规格：合同文字只在 `CONTRACTS.md` 保留一份，测试只比对这一份；验收台账与裁决表改为 `tests/` 下的数据文件，不再从散文里解析。否则直接归档会让约 20 个测试函数失败。
- 按目前的文档量估计，约 26.6k 行转为归档（其中 21.2k 行本来就是历史性文档），现行文档约 25k 行。
- `tests/test_dayrun_fidelity_acceptance.py` 对 `docs/dev/research/` 路径有豁免，选定归档目录时一并处理。
- 建议从最独立的工具交互特性开始，走通一次再推广。

### 风险

- **先报告后拦截：** 2.1 与 2.2 的检查先以「只报告」上线，列出现有问题（78 处符号引用、348 处现行文档行号、代码对文档的引用），修完再改为失败，避免一次改动过大。
- **路径变化的连锁影响：** 归档会改变文档路径，INDEX、`CLAUDE.md`/`AGENTS.md` 的入口与汇编版设计说明书的附录摘录（`scripts/build_design_doc.py` 的 `APPENDIX_SECTIONS`）都可能受影响；按 `AGENTS.md` 要在同一提交重新汇编。
- **命名规则：** 嵌套函数、再导出与类属性的限定名需要统一规则，`RELOCATED` 表本身也要由门禁检查。
- **合并改变版本：** 并入修订会让基础规格的版本表增长，引用规格章节的代码与测试需要按 2.2 同步。

### 验收

- 现行文档没有 `.py:数字` 引用；全部 `::` 符号引用与代码、测试对文档的引用都能解析。
- 历史文档都有完整提交号基线。
- 147 条突变用符号锚点生成的变异源码与迁移前逐字节一致，突变审查结论不变。
- 指向生产代码的文本钉只剩接口导入断言与 `ast` 结构检查。
- 工具交互特性完成合并与归档，相关测试改读新位置后全量通过。

## 三、测试分层：按实测耗时分快速、标准、全量三层

### 现状（实测）

本次在基线上把全量测试分片并行跑了一遍，用 JUnit 记录每个用例的耗时。分片时每个目录的测试文件保持连续，避免 `engine_factory` 夹具丢失。机器为 6 核 12 线程，6 个分片同时运行，单个用例的耗时因此比单独运行时偏高。

1. **规模与耗时：** 共 5,858 个用例，5,850 个通过、7 个跳过、1 个错误。这个错误与被测代码无关：一个测试用硬链接复制语料，仓库与临时目录不在同一磁盘卷时就会失败（见[共享规则单一归宿与可重建环境提案](PROPOSAL_2026-10-04_SHARED_RULES_AND_REBUILDABLE_ENV.md) 5.5）。用例耗时合计 313 分钟，约 5.2 小时。按文件名顺序分成 6 片并行时，5 片在 14–57 分钟内完成；第 6 片（`tests/life` 的后三分之一）跑了 79 分钟只完成 745/1,105 个用例，改为 6 个子分片重跑，其中最慢的子分片（含 `test_tool_layer.py`）也用了 49 分钟。改一行代码想得到完整反馈，要等一个多小时。
2. **耗时极度集中：** 4,194 个用例（72%）每个不到 1 秒，合计只要 5 分钟；其余 28% 的用例占了 98% 的时间。

| 类别 | 用例数 | 耗时（分钟） | 占比 |
| --- | ---: | ---: | ---: |
| 建世界的用例（`engine_factory` 所在文件中 1 秒以上的） | 1,289 | 220 | 70% |
| 源码突变审查（每条登记突变一个子进程） | 147 | 51 | 16% |
| 完整自然日（`tests/integration/test_dayrun_complete_days.py`） | 2 | 20 | 6% |
| 其余 1 秒以上的用例 | 226 | 16 | 5% |
| 1 秒以内的用例 | 4,194 | 5 | 2% |

3. **源码突变审查跑在普通测试里。** `tests/test_errands_workday_acceptance.py` 与 `tests/test_tool_interaction_acceptance.py` 为每条登记突变启动子进程，再跑一遍被登记的行为用例；单条最长 857 秒。它们是特性验收的审查证据，不是每次改动都需要的回归测试。
4. **建世界的用例慢在两处：建世界的夹具，以及每次观察。** 建世界的用例平均每个 10 秒，其中建世界约占 3 秒，其余主要是推进与观察。
   - **夹具重复读取冻结输入。** 单独测得 `engine_factory` 建一个引擎约 2.8 秒，大头是冻结输入：组装场景语义（目录加载与对象编译、地图、门店供给）、语料清单逐文件核对 975 个文件，以及引擎初始化时读取 193 份字幕。夹具为写运行身份先完整调用一次 `load_scenario`，`LifeEngine.create` 随后又完整组装一次。这些输入在整个测试会话里都不变；生产路径的 `create` 只读一次，问题在夹具。
   - **单次观察本身就贵。** 在刚建好的世界上，一次 `observe` 约 0.4–0.6 秒，并随事件增多而变慢（连续三次分别为 0.37、0.47、0.56 秒）。剖析显示时间主要花在每次都重算的纯函数上：为只读查询重算全部门店供给行（`discovery.supply_row` 1,293 次）、重复解析品类配对（`resolve_pairing` 2,754 次）、深度冻结容器（约 5,500 次）。一个用例常要观察几十次；`test_tool_layer.py` 的 20 个用例平均每个 83 秒。真实运行里的每次决策同样付这笔成本。
5. **没有并行与超时工具。** 开发依赖只有 `coverage`、`pytest` 与 `pytest-asyncio`。新增依赖会改动 `uv.lock`，而 `uv.lock` 计入运行身份，所以哪怕只加一个开发依赖，也会让已有检查点不能续跑。

### 方案

**3.1 夹具只读一次。** 运行身份只需要场景的人物编号、起止时刻与时区。夹具改为直接从场景文档读这几项（或复用一次组装的结果），不再为此完整调用 `load_scenario`。只改测试代码。

**3.2 测试会话内缓存冻结输入。** 在 `tests/life/conftest.py`（及其他使用同一夹具的目录）加一个会话级缓存，按文件摘要缓存 `load_runtime_scenario` 的结果与语料清单的核对结果，测试中的 `LifeEngine.create` 经由这层缓存取得：

- 只缓存不变的冻结输入（组装后的场景语义、语料清单核对结果、字幕）；世界状态与足迹存储照旧每个用例新建。
- 缓存前先确认这些对象是深度不可变的。`life` 的 `FrozenModel` 只禁止字段重新绑定，不冻结内部容器；若有可变容器，就对缓存结果做深拷贝再交给用例。
- `mutate` 改写场景的用例不走缓存。顺带把 `_mutated_scenario` 复制整个 `catalog/` 目录改为只复制场景文档，目录按绝对路径引用。
- 若要让生产代码提供缓存入口（例如给 `create` 传入已组装的语义），按 `AGENTS.md` 先改所属规格；只在测试侧做缓存则不涉及生产行为。
- 按剖析估计，3.1 与 3.2 合起来每建一个引擎可省约 2 秒，对 1,289 个建世界的用例合计约 45 分钟用例时间。上线前用本节的计时方法实测一次。

**3.3 标记自动生成，不靠手写。** 在根 `conftest.py` 的 `pytest_collection_modifyitems` 里，按用例的实际依赖自动打标记，新增用例不必记得手动标：

- `engine`：用到 `engine_factory`，或导入并驱动 `LifeEngine`、`LifeEnv` 的用例。
- `mutation`：执行源码突变审查的用例。突变登记的格式检查不带此标记，仍在快速层。
- `day_run`：完整自然日与多日运行。
- `external`：需要 Node、LabelKit 虚拟环境或 TextWorld 的用例。

**3.4 三层的定义：**

| 层 | 何时运行 | 内容 | 目标耗时（6 个进程） |
| --- | --- | --- | --- |
| 快速层 | 每次改动、提交前 | 不带 `engine`、`mutation`、`day_run`、`external` 标记的全部用例（约 4,200 个），加上直接导入被改模块的测试文件中的 `engine` 用例 | 3 分钟以内 |
| 标准层 | 合并前 | 除 `mutation` 与 `day_run` 外的全部用例 | 现状约 40–45 分钟；3.1–3.2 之后约 35 分钟；3.7 的收益取决于观察在用例耗时中的占比，剖析后再定目标 |
| 全量层 | 每日、发布前、特性验收 | 全部用例、覆盖率门禁、文档与设计说明书门禁、源码突变审查 | 不设上限，结果留档 |

「直接导入被改模块」按测试文件的导入静态求出。`life/` 目前在逻辑上是一个整体（第一节），按传递依赖挑选会选中几乎全部用例，所以快速层只取直接导入；合并前的标准层兜住其余影响。

**3.5 一个运行脚本，三层与覆盖率门禁共用。** 新增 `scripts/run_tests.py`（只用标准库），参数 `--tier fast|standard|full` 与 `--workers N`：

- 按全量层记录的各文件耗时分片，而不是按文件名顺序，把最慢的分片压到接近平均值；本次按文件名分片时，最慢一片的用时是最快一片的五倍以上。每个目录的测试文件仍保持连续。
- 用 `sys.executable -m pytest` 启动各分片，结束后汇总结果与耗时。
- 覆盖率门禁改用同一脚本，加上 `coverage run -p` 后合并，与[共享规则单一归宿与可重建环境提案](PROPOSAL_2026-10-04_SHARED_RULES_AND_REBUILDABLE_ENV.md) 5.4 一起实施。
- 不引入 pytest-xdist，理由见现状第 5 条。

**3.6 防止层次失效。** 全量层每次输出各用例耗时，写入 `docs/dev/` 下的耗时报告（生成物）。报告列出落在快速层却超过 1 秒的用例，以及标准层的总耗时，超出目标即提醒；`scripts/run_tests.py` 的分片也读这份报告。

**3.7 降低单次观察成本（生产代码，单独立项）。** 剖析指向的都是对同一份冻结语义反复求值的纯函数：品类配对解析、门店供给行与购买系数。可以按语义版本缓存它们，供给行按世界的供给版本增量更新。这能让测试与真实运行同时受益，但改的是生产代码，按 `AGENTS.md` 另写规格；验收要求同一脚本化运行的观察与导出逐字节不变。

### 风险

- **缓存共享状态：** 若冻结对象里有可变容器又被某个用例改动，会在用例之间串扰。缓解办法是先做不可变性检查或深拷贝，另加一个守卫用例，在会话结束时核对缓存对象的摘要没有变化。
- **漏跑：** 快速层只挑直接导入被改模块的 `engine` 用例，跨模块的影响可能漏掉。合并前必须跑标准层，这一条写进 `docs/VERIFICATION.md`。
- **验收证据的口径：** 突变审查移出日常运行后，特性验收仍按 `docs/VERIFICATION.md` 在全量层执行并记录，验收要求不降低。
- **测试路径与生产路径的差别：** 缓存让测试里的 `create` 跳过了真实的组装与清单核对。保留一组不走缓存的用例（新建与恢复运行各一个），确保生产路径本身仍被覆盖。

### 验收

- 快速层在 6 个进程上 3 分钟内完成，标准层达到 3.4 的目标，全量层的用例数与改动前相同且全部通过。
- 用本节的计时方法复测，建世界的用例平均耗时下降，缓存守卫用例通过。
- 覆盖率门禁只用 `scripts/run_tests.py` 与虚拟环境的 Python 即可运行。

## 本次核查做了什么

- **依赖结构：** 用 `ast` 解析 `src/worldmock` 与 `custom` 的全部导入，区分模块级导入、函数内导入与 `TYPE_CHECKING` 导入。按模块级依赖给 `life/` 分层，再逐条判断函数内导入是否闭合成环，并验证其余函数内导入同时上提不会产生新环。读取 `LifeEngine` 与三个 Mixin 的方法和私有成员使用，统计测试对引擎私有成员的访问。
- **文档与测试的引用：** 提取文档中的行号引用与符号引用，按 INDEX 状态列区分现行与历史文档，分别在 HEAD 与各文档声明的基线上核对；读取突变登记与 `tests/mutation_runner.py`，用原型验证符号作用域锚点对 147 条突变生成相同的变异源码；统计读取生产源码与文档文字的测试。这一部分没有修改任何文件。

- **未核实：** 冻结输入对象是否深度不可变（3.2 的前提）；拆分 `LifeEngine` 后的行数按方法簇估计，没有做原型。
