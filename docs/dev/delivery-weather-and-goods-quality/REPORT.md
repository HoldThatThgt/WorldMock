# 外卖配送与到手品质 · 交付记录

[开发规格](SPEC.md)列出行为、改动文件和验收方法。[原提案](PROPOSAL.md)保留了人物视角和模拟数值的来源。

## 从查询到收货

固定 4,200 米、大雨和同一家店，12:00 查完菜单并下单。真实查询给出掌柜的店、4 分、12:27 预计送达。人物付款 51 元，12:30 的进度记录显示天气使配送多用了 6 分钟，比下单预计晚 3 分钟。该份信阳山笋炒腊肉的收货品质为「中」。

另一笔两份牛肉面的外卖在大雨中下单，23:59 是公开预计。零点恢复时天气已放晴，订单仍在途，00:02 才出现一次延误说明和两份独立的收货品质。恰在零点查完的新报价用当天天气。一笔相同身份的快递在晴雨两种情况下按相同时刻到站，领取时沿用原有收货事实。

两家同类型面馆分别设为二星和四星，到店和外卖都买同一道牛肉面。每家店、每种履约方式各用 1,024 个固定订单身份，三档频率与理论概率的差异均在 4 个百分点内。

## 审查与修正

最终在 Windows 上通过全部 6,739 项测试，零失败、零错误、零跳过。合并分支覆盖率 96.26%，公共接口未覆盖数为零。当前文档链接检查与设计说明书 HTML 构建均通过。

规格审查修正了发货时间的文档口径。实施审查发现，查询恰在零点完成时会早于当天的天气事件读取天气。已将天气登记提到进入新一天的时刻，沿用原有天气事件次序。继续运行和恰在零点截止两种路径均有回归测试。

审查涉及的 96 项回归检查通过。两种完整日的冻结基线各经两次独立运行比较一致后发布。全部 313 个源码变异用例均识别了预期的错误实现。

运行验证时，Windows 沙箱阻断了 Python 异步事件循环依赖的本机回环连接，完整测试在获准的本机环境执行。两项 Git 身份检查要求临时工程在仓库之外，复验该组时使用 pytest 默认的系统临时目录。

## 收尾模型样例

同一人物在四季便利买了一份 12 元的柠檬茶，商铺评分为 3.5。两次从收货到宿主构建收尾请求均经过实际引擎。在测试中只控制正态抽样值，得到一份好、一份坏。自动比较了完整系统消息、可用工具和人物消息，人物消息仅有该份收货的品质一字不同。

两个独立的 Codex 会话模型实例各读取其中一份原始请求，各自选择 `conclude_activity`。其参数分别通过原请求自带的工具格式校验。以下是各自写进「看法」的原文。

| 收货品质 | 人物写下的看法 |
| --- | --- |
| 好 | 四季便利这杯柠檬茶挺合我口味，12元花得值。下回上班路过还愿意买。 |
| 坏 | 四季便利这杯柠檬茶真难喝，花12元挺冤。下回想喝柠檬茶，我会换家店。 |

这对样例检验了人物能否在店铺评分相同的情况下区分体验。引擎保存的事实止于商品、商铺和品质，口味、值不值和再次购买的意愿都是模型自述。原始请求及两个工具调用保存在本次 worktree 的 `.work/goods-quality-model-pair/`。自动审批拒绝向外部 DeepSeek 服务发送包含完整人物上下文的请求，因此这对样例来自当前 Codex 环境，未测外部供应商。

## 无人值守时采用的决定

| 问题 | 采用的处理 |
| --- | --- |
| 哪些地点填评分？ | 按已有商品绑定逐地点判断。在店内售货但没有下单 app 的地点也要填写；纯代收站省略，兼营商铺的驿站对其出售的商品填写。 |
| 哪份环境随此次发布？ | 更新 WorldMock 仓库自带的完整示例环境和制作手册，评分均为显式合成值。独立的 WorldMock-Dataset 有自己的环境版本和主分支，此次交付以 WorldMock 的 main 为目标。 |
| 付款导致晚到怎么说明？ | 天气延长只取受理时冻结的值；比预计晚多久取实际到达与公开预计之差。零天气延长时仅解释晚到。 |
| 恢复和重新观察如何处理？ | 世界状态结构随订单字段从 15 升至 16。订单存冻结的公开预计和外卖私有延长，收货事件按份存最终品质。恢复继续按同一笔订单交付。 |
| 评分与模型看法如何验收？ | 固定订单身份按理论三档概率验证抽样；在真实人物输入中验证逐份事实，再观察一对模型收尾。测试不要求任何固定的购买意愿。 |
