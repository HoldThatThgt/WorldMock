### 2　`no_restarted_activities`：10-09 22:45 的微信读书

#### 经过

- **21:45，开始。** 第 485 轮开始微信读书（事件 2540–2542），计划时长 40 分钟（`planned_duration_seconds` 2400）。
- **22:15，继续。** 第 488 轮用 `report_status` 让它继续（2553），自述写「已经读了约三十分钟，还剩一小段，读完这章就去睡前洗漱」。
- **22:45，第 492 轮收尾。**
  - 唤醒原因是 `progress_report_due`，观察是 2566。工具层这项活动写着「已用约 1 小时，放到第 3 条」。
  - 思考（响应 2569）把开始时的 40 分钟当成了这次阅读的长度："~40 min duration, so should be ending around 22:25"。它决定收尾，并且已经打算重开："maybe continue reading another chapter (start side activity 微信读书 again) — that seems repetitive but reasonable given 清醒"。
  - `conclude_activity`（2570）之后，活动以 cancelled 结束（2574、2575）。
- **22:45，同一秒的第 493 轮重开。**
  - 观察是 2577，这是一次同秒续接：请求 2579 依次是 system、user、assistant、tool 四条消息。
  - tool 消息写着结果「结束使用」。「今天」多了 22:45 一条，核验「微信读书 21:45–22:45，《软件工程入门·需求与评审》等2条」，后面跟着它自己写的看法。
  - 思考（2580）写："repeated reading right after concluding seems odd; but it's a content app that continues to next piece … I'll continue reading."
  - 随后 `start_side_activity` 开始微信读书（2581、2582）。
- **之后。** 新的一段读到 23:29:57，由第 498 轮收尾（2605、2609）；第 499 轮开始睡前洗漱（2616）。

#### 计数是对的

`_restarts`（tools/analysis/memory_pilot.py:1303）的规则是：一项活动的结束落在上一次决策的观察（2566）和这一次决策的观察（2577）之间，而这一次决策又受理了同一个目标，就计一次。2574 正好落在这个区间里，所以计 1。独立写的复算（`analysis-2/restarts.py`）也得到 1。

#### 原因：模型的选择，不是记忆缺失

- **人物知道刚收尾。** 它从三处看到了：链里自己的上一回合、工具结果、「今天」的新条目。它也明说重开显得奇怪，还是重开了。
- **触发点。** 它把开始结果里的 40 分钟当成了这次阅读的长度，于是收尾；22:15 那次它用的是 `report_status`。
- **与本次改动无关。** 两次引擎之间，决策提示只改了上面那一句讲回顾的话；这个提示里「近三天」的各格也与阅读无关。

## 两项为 null 的检查：`search_memory` 没有被调用

- **没有一次调用。** M5 的各项都是 0。全部 419 次决策回合的响应（304 次新决策、115 次带历史）里没有 `search_memory` 调用，可这个工具在 419 次请求的工具表里都有。出现过的工具名只有 5 个：`start_main_activity`、`start_side_activity`、`report_status`、`conclude_activity`、`pause_activity`。思考文字里也没有提到 `search_memory` 或「未整理」。
- **为什么没有调用。** 系统规则写着「近三天以外的用 search_memory 查」，并说明检索时「某天某一类「未整理」时给那天的原始条目」；它没有直接要求遇到「未整理」就去查。本次每个吃饭问题都能从「近三天」答出来：饮食格没有一格「未整理」，而 5 天的窗口里，只有到 10-12 时 10-08 才落到三天以外。缺着的工作和生活格，人物没有用到。
- **第一次的检索都是缺口引起的。** 9 次调用分在 3 次决策里：
  - 10-09 08:20：「近三天工作未整理。可以查 search_memory」（1563）；
  - 10-11 11:30：近三天里只有 10-08 的饮食，它和当天计划对不上（10-08 的清蒸鲈鱼对计划的宫保鸡丁）；
  - 10-12 11:46：「近三天未整理，可以用search_memory查」（5991）。
- **V 不可比。** V 没有这个工具，只调用过 2 次旧的 `memory_search`。
- **结论。** 0 次调用正是这个设计在本次输入下应有的结果，但 `search_validation_errors` 和 `search_non_empty` 因此没有检验到。要检验它们，需要 `lm-variety-10day` 那样三天以外确实有事可查的运行。

### 重试为什么压不下来

- **反馈说了长度，但没说要删多少。**
  - 每条问题的写法是 `digests.{key}.text has {len} characters; the {tier} digest limit is {limit}`，例如 3949 带的 "digests.work.text has 202 characters; the day digest limit is 200"。
  - 它给了当前长度和上限，没有给超出多少、目标多少，也没说标点算不算。
- **第一轮反馈后降得多，之后降得少。**
  - 收到长度反馈后，16 段后续正文都不比前一段长。
  - 第一轮（9 格）降到 169–224 字，5 格通过（169–198），4 格没过（202、217、218、224）。
  - 之后的 7 次删得很少，与告知的超出量无关：

  | 被告知 | 下一次 | 删去 |
  | --- | --- | --- |
  | 217 | 205 | −12 |
  | 218 | 209 | −9 |
  | 209 | 203 | −6 |
  | 202 | 202（逐字相同） | 0 |
  | 202 | 193 | −9 |
  | 224 | 222 | −2，只删了「又」「倒」两个字 |
  | 222 | 217 | −5 |

  平均约删 6 字，7 次里只有 1 次到了上限以内。
- **模型很可能按「字」不计标点来数，这是推测。**
  - 收到长度反馈后写的 16 段，汉字都只有 149–196 个。
  - 仍然失败的 10 段，汉字 179–196 个，加上 20–28 个标点，`len` 才到 202–224。
  - 41 段里标点占 `len` 的 8.5%–12.6%，中位 10.7%。
  - 规格把「字」定为 `len()`；提示写「不超过 200 字」，错误文字写 "has 205 characters"，都没有说标点也算。这与「模型的目标是约 200 个汉字」相符，但证明不了。
- **重试不带历史。**
  - 每次重试只有原始的 2 条消息加 1 条纠错消息（runner.py:763 由 `original` 构造），前几次的错误和正文都不带，也不告诉模型这是第几次。
  - 纠错消息由 `correction_message` 组成，含 `INSTRUCTION`（"Return a complete new submit_memory_digest tool call using the unchanged schema."）、`PREVIOUS_INVALID_RESPONSE`（上一次的完整原始响应）和 `VALIDATION_ERROR`。
- **已通过的类也被重写。** 错误只列没通过的类，不说哪些已经通过。模型把已通过的类又重写了 10 次，约 1,685 字的输出白费了，有时还改了内容：10-10 饮食 200 → 141 → 141 → 133，10-11 饮食 168 → 148。代码不看这些重写，登记的仍是第一次通过的正文。
- **响应级错误吃掉了一轮反馈。** 1384 的三个调用各缺键，整次按响应级错误拒掉，三类正文（258、272、240）都没有经过长度检查。下一次请求 1385 只带着 "response must contain exactly one submit_memory_digest tool call" 这条错误，1386 的饮食和工作反而写得更长（258 → 280、272 → 287），生活 240 → 230。结果 10-08 工作只得到两轮长度反馈（告知 287、217），而不是三轮。

### 输入大小不能预示超长

- **只通过类别起作用。** 饮食输入最小（14–21 行，1.6k–2.5k 字），没有 fallback。
- **类别以内看不出关系。** 去掉饮食后（n = 7），输入字符数与首次尝试长度（10-08 取第 1 次响应原文）的 Spearman 相关是 0.11，输入行数是 −0.04（并列取平均秩）；10-08 改取第 2 次时分别是 0.18 和 0.00。
- **反例。** 最大的输入 10-11 生活（80 行，11,895 字）第 2 次就以 169 字通过；三个 fallback 格的输入在非饮食的 7 格里排第 2、3、5 大（5,460、5,018、4,727 字）。
- **与 fallback 对得上的是首次重写的长度：三个 fallback 格正是首次重写最长的三格（217、218、224）；输入最大的那格（10-11 生活）没有落空。**

**日记设计在这次运行上起作用了：**
- **回顾写出来了。** 11 个类·日写出 8 个，第一次是 1 个。
- **饮食格没有缺。** 昨天的饮食格 322/322 是正文；「近三天」三分之二是正文，第一次只有 11%。
- **形式对了。** 正文是第一人称的日记，没有 HH:MM、编号或标签列表。
- **内容是真的。** 模型核对没有找到矛盾或编造。
- **人物用上了。** 它按日记安排吃饭、做食材包，甚至按日记里的一处感受早睡。第一次那两处因缺回顾而做错的决定没有再现，吃的 17 样各不相同。

**和第一次相比改进在哪里：**
- **守卫的问题消失了。** 第一次 10 格落到「未整理」：3 格只因数字同条、做饭那一句等句子规则拒掉了事实正确的正文，6 格是初稿 314–746 字、四次压不到 200 字或参数结构不合，1 格两者都有。这次长度以外的守卫丢弃是 0，参数结构错误也是 0。

**还没有通过的，以及原因：**
- **长度（`digest_fallback_share`）。** 三格各差 3、5、17 字。
  - 收到长度反馈后，模型只做小修小删，有一次原样重交。
  - 三格最后一次只数汉字是 182、179、190 个，很可能是把「字」理解成不算标点。
  - 反馈只说长度、不说要删多少，重试也不带历史。
  - 10-08 那一格还因响应级错误少了一轮反馈。

  上限不变的前提下，最直接的改法是让反馈写明超出量和标点也算（O1），或者多给两次重试（O5）。两者都要负责人裁定。
- **重启（`no_restarted_activities`）。** 这是一次模型选择，它自己说了这样做显得奇怪。它与记忆设计无关，严格口径在第一次和 V 都是 0；但这一项按规则仍是 false。
- **日记的形式还有两处不合提示，运行时按设计不查。**
  - 10/11 格写了中文钟点；
  - 压长度时先删感受（10-08 饮食删光了前两次写过的看法，10-10 工作删掉了唯一一句感受）。

**这次运行不能说明的：**
- **检索有没有用、会不会出错。** 0 次调用，两项检查为 null；5 天窗口里没有需要检索的缺口。
- **三天以前的回忆和月回顾。** `lm-variety-10day` 和 `lm-variety-cross-month` 没有跑。
- **人物行为的改善是不是设计带来的。** 没有 `lm-baseline-*` 对照，每种设计只跑了一次；17/17 的多样性和 0/4 的午饭重复，可能有一部分是抽样波动。
- **日记措辞流进自述会不会形成循环。** 本次已经有 20 次决策的自述带着日记片段，按天在增加，五天还看不出结果。
