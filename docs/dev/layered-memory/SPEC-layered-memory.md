## 负责人的指示

人物应当像真人一样记事：今天每次决策留一条，过了零点按饮食、工作、生活三类压成一段回顾，最近三天的回顾放进提示，更早的按类别和时间去查；系统提示要教人物怎样用这套记忆。负责人要求写出详细的开发规格并按它实现，不让规格偏离提案，不把待办的实现往后推，并用测试保证这一点，也不做规格以外的东西。据此：

- **一次交付终态。** 提案的 P0、P1、P2、P3 一起交付，分期只决定实施次序。提案为 P1、P2 准备的临时规则写法，以及 P1 期间沿用现行层序、看法暂留人设层、条目暂不渲染「看法·」等过渡形态，都不实现。P4 不做。
- **验收靠确定性测试。** 真实模型试点（提案约 $14）不在这次任务里执行；试点的规程与指标写在第 09 章，以后执行。
- **LabelKit-DataSet 由它自己的会话改。** 本规格写明它要改的那一处和发给它的通知；WorldMock-Dataset 的五个包和构建工具按第 08 章改。
- **「字」是 Python `len()` 的字符数。** 每条今天条目的 120 字只数「核验」和「自述」里的字符串（裁定 19 的读法）。
- **仓库规则照旧。** 不留兼容、回退与迁移，过时代码直接删除；每条规则只在一处；`docs/design/` 是当前行为的唯一权威，与代码、测试同一次提交（AGENTS.md）。

## 术语

| 术语 | 含义 |
| --- | --- |
| 决策 | 一个人物按 `decision_id` 分组的世界请求；任何世界请求都结束一次决策（含 report_status、revise_day_plan 与被拒的请求），只读查询不算（第 02 章【E1】） |
| C_j | 第 j 次决策的提交末事件序号：`store.commit_last_seq` 作用在这次决策的第一条结果上（第 02 章【E2】） |
| B_D | D 日的零点界：D 日本地 00:00 之前最后一个事件的序号，只由 `day_bound` 求出（第 03 章） |
| P_k、已发布界 | 第 k 次决策观察里的 max(C_{k−1}, B_D)；序号不超过它的事件已写进「今天」的条目或属于前一天，进度层的事实只写序号大于它的（第 02 章【E5】、第 06 章【P1】） |
| 今天条目 | 每次决策一条，`{"时刻","类别","核验","自述"}`；第 k 条从第 k+1 次决策起可见，包括同秒链里的下一次决策（第 02 章） |
| 核验、自述 | 核验是环境从已提交事件写出的短句；自述是人物当时写下的话，带「〈名称〉：」「进展·」「看法·」「记住：」「正文：」前缀 |
| 全文 | 条目不截断、不渲染的形状：完整核验行、「当时查到」与全部自述（含 routine 记忆）；供回顾输入、检索「今天」与「未整理」退路（第 02 章【E33】） |
| 零点收尾条目 | D 日最后一次决策之后到零点之间的已结算事实，加每项跨过零点仍在进行的活动一句「跨过零点」；「时刻」写 `24:00`，只有全文，从不进提示（第 02 章【E36】–【E39】） |
| 回顾 | 模型在零点写的段落：日回顾每类 ≤200 字，月回顾 ≤800 字，年回顾 ≤2000 字；记成 `memory_digest_generated` 事件；是整理出来的回忆，不是核验事实（第 04 章） |
| 近三天 | 记忆层里每类最近三天的日回顾：饮食和生活取日历上的前三天，工作取最近三个有工作记录的日子（第 03 章） |
| 可查 | 记忆层里 `{"最早日期": 运行开始的本地日期}`（第 01 章） |
| 未整理 | 某一类某一天的回顾校验重试用尽、没能写出：这一格写 `"回顾":null,"未整理":true`，按日期检索时退回那天这一类的原始条目（第 03、04、05 章） |
| 类别、类别串 | 饮食、工作、生活三类，由代码从冻结目录、人物声明和已提交事件推出；条目的类别串以主请求的类别打头，其余按首次出现的次序以「、」相连（第 03 章） |
| 规则 B | 每条 120 字以内的取舍：「先给每条开头」，首轮每项 40 字、50 字以内整项给，余量回补，截断处以「…」结尾（第 02 章【E24】–【E30】，裁定 27） |
| 兜底 | 两种：记忆层兜底是「今天」接上一条后整层超过 14,000 字时一次回落到 12,000 字以内的三步（第 01 章，裁定 24）；核验兜底是一条条目的核验本身超过 120 字时的三步（第 02 章【E20】） |
| 带入记录 | 进度层里不看下界的开始请求记录：占槽位的本人活动（不分种类）与这段停留或路程里做完的查询（第 06 章【P4】【P5】） |
| 在途订单 | 已付款、状态为 `pending` 或 `ready_for_pickup` 的商品履约记录，列在待办层 `orders`（第 06 章） |
| 食材包 | 食材包状态（`reset_on_goods` 非空的食品状态）的重置商品；做饭用的是开始前同一状态最近一次重置的那一份（第 08 章） |
| 字 | Python `len()` 数出的字符数 |
| V、B | 提案的两次证据运行（人物卡片含与不含「每顿饭都愿意换着尝不同的菜」），2026-10-08 → 10-13 |

## 人物会注意到什么

| 情形 | 现在 | 之后 | 章 |
| --- | --- | --- | --- |
| 回想今天做过的事 | 记忆层按已结束的停留各列一条，前一晚的事挂在今天名下；当前停留里的决策只在进度层 | 「今天」每次决策一条，按时刻排、写明类别，核验与自述分开，每条至多 120 字；一提交，下一次决策就看到 | 01、02 |
| 回想昨天和前几天 | 只有睡醒反思的感想和未结订单，傍晚常被 8000 字窗口删掉；零点前结束的停留里的饮食第二天看不到 | 「近三天」每类每天一段零点写好的回顾，整天不变；回顾没整理出来时写明「未整理」 | 03、04 |
| 想查更早的事 | 三个 `memory_*` 工具只查 episodes.jsonl，多个关键词查不到；V 两次检索都为空 | 唯一的记忆工具 `search_memory`：按类别、某一天、一段日子、某月、某年、今天或今天的一段时刻查，可加关键词；查到的往日是回顾，「未整理」的那天给原始条目；一次决策至多三次 | 05 |
| 人设层 | 带着一路累积的偏好与关系看法（V 结束时 40 条、约 4k 字） | 只有人物卡片，整次运行逐字节相同；收尾写的看法当天在「今天」，之后在回顾里 | 07 |
| 进度层 | 整段停留的全部工具记录，中位约 14.7k 字 | 只有还没了结的事和上次决策之后才到的事：占槽位的活动、新到的结果与消息、这段停留里做完的查询，以及今天被拒的请求 | 06 |
| 待办层 | 暂停的活动、个人事务、今日计划 | 另列在途订单，至多六行 | 06 |
| 家里做的饭 | 结果里只有目录摘要「比如番茄炒蛋、清炒上海青……」，人物照抄进自述 | 开始与完成结果、今天条目和零点计划都写出用的是哪天收到的哪份食材包；包 0001 的摘要不再点名菜式 | 08 |
| 请求的层序 | 工具、人设、记忆、待办、环境、进度 | 人设、记忆（可查、近三天、今天）、待办、工具、环境、进度；稳定的在前 | 01 |
| 系统层规则 | 20 条，讲记忆的只有零散几句 | 22 条：各层写什么、记忆层怎样组织怎样查、拿不准时怎样看记忆（不替人物决定）、核验与回忆的区别 | 07 |
| 当天第一次睡醒 | 先做一次记忆巩固和就寝反思的模型调用 | 不调用模型，直接决策；往日的整理在零点由回顾承担 | 08 |
| 原生工具 | 十个 | 八个 | 05 |
| 同一秒接着决策 | `changes` 里有人设的看法与偏好 | `changes` 加上上一决策的条目（`memory.added`）和在途订单；「今天」被兜底改写时改用新快照 | 06 |
| 在公司吃午饭 | 没有食品信号，按地点会算作工作 | 包 0001 给它标饮食 | 03、08 |
