# 买菜做饭：收货开放的地点内容与完成效果

> 状态：方向已由所有者定下（2026-10-12），细节按本文建议写成，等所有者确认；本文不改变任何现行行为。
> 日期：2026-10-12。

> 代码基线：主干提交 `79304ff7`。文中的「今天」都指这个提交。
> 证据层级：读代码。没有调用模型，没有做过真实运行。

<a name="proposal-grocery-cooking-结论先看"></a>
## 结论先看

- 人物买了食材，收货时不加能量；家里多出一件「做饭」，什么时候做由人物自己决定，做完才补能量。
- 不做库存。买一件食材还是十件、买一次还是三次，都只开放一次「做饭」；开始做饭就用掉，想再做要再买。
- 引擎只提供机制。什么商品开放哪件事、做完有什么效果，都由数据集写，引擎不认识「食材」和「做饭」。
- 机制拼在已有的回调状态上：收货把状态置为上限，这一半今天就有。地点内容新增两个可选字段：
  `consumes_state` 让这件事凭状态出现、开始时用掉；`completion_effects` 写这件事做完时的一次性效果，只写档位名，不写数值。

<a name="proposal-grocery-cooking-现在是什么样"></a>
## 现在是什么样

| 机制 | 今天的行为 | 对「买明天的食材」的后果 |
| --- | --- | --- |
| 食品收货 | 零食 200 千卡、食品 600 千卡，收货当秒补能 | 食材包标成食品，一到就被当成一餐吃掉 |
| 商品收货 | 只减 0.10 放松需要 | 食材包标成商品，人物永远吃不到它 |
| 地点里做的事 | 体力档位按实际小时消耗能量，两项缓解档位按实际小时缓解；做完那一刻没有任何效果 | 数据集里的「做晚饭」做完，人物仍然饿 |
| 回调状态 | `callbacks.jsonl` 的状态有初值、上限和 `reset_on_goods`；收到所列任一商品就把状态置为上限，状态增量规则和阈值提醒可以订阅它 | 只有回调规则读状态，地点里做什么不看它 |
| 驿站 | 包裹到站后，本人在驿站点名一件事时领取；没有到站包裹时，那里的事都做不了 | 「收到东西才能做某件事」今天只有这一个写死的特例 |

所有者原话：「the grocery or the cooking content are supplied by the dataset, the system's job is to make such hook system available」。

驿站同样靠地点行上的一个字段 `accepts_parcels`，其余由引擎写死：快递商品送到离家最近的驿站，到站后在那里开始一件事就领取。
引擎能写死，是因为两头都归引擎；买菜做饭的两头都归数据集，所以「哪些商品开放哪件事」必须由数据集写在某处，这就是 `consumes_state`。

<a name="proposal-grocery-cooking-改成什么样"></a>
## 改成什么样

```mermaid
flowchart LR
    Buy[收到任一登记的食材商品] -->|已有：reset_on_goods 置为上限| S[状态 groceries = 1]
    S -->|新增：状态不小于 1 时列出| U[家里出现「做饭」]
    U -->|"start_main_activity(interact, 家, 做饭)"| A[受理：状态减 1，「做饭」不再列出]
    A --> D[做完：按档位补一餐]
    D -.->|再买一次| Buy
```

| 环节 | 谁写 | 今天有没有 |
| --- | --- | --- |
| 收到食材，状态置为上限 | 数据集在 `callbacks.jsonl` 写一个状态，`reset_on_goods` 列出食材商品 | 有 |
| 状态不小于 1 时，家里列出「做饭」 | 数据集在做饭那条内容上写 `consumes_state`；引擎负责列出、隐藏和拒绝 | 新增 |
| 开始做饭，状态减 1 | 引擎 | 新增 |
| 做完，按档位产生效果 | 数据集在那条内容上写 `completion_effects` 的档位；引擎按固定数值结算 | 新增 |

### 完成效果只写档位

所有者原话：「the stat effect in "completion_effects" should use tier name also, no explicit value」。
档位全部沿用引擎已有的两套，不新增任何数值：

| 成员 | 档位 | 做完时的效果 | 沿用的既有档位 |
| --- | --- | --- | --- |
| `food` | `snack`、`meal` | 补 200 或 600 千卡，按食品利用率和 2400 千卡上限结算，和收到一件同类商品相同 | 商品类别零食、食品的收货热量 |
| `relaxation_relief` | `low`、`medium`、`high` | 放松需要一次减少 0.10、0.30、0.50，不低于 0 | 内容按小时缓解的同名档位，做完一次等于这一档缓解一小时 |
| `social_relief` | `low`、`medium`、`high` | 社交需要一次减少 0.10、0.30、0.50，不低于 0 | 同上 |

每个成员都可以省略，省略就是没有这项效果；档位 `none` 不收，「没有」只有省略一种写法。
内容行上原有的 `exertion`、`relaxation_relief`、`social_relief` 不动，仍按实际做了多久结算：做到一半得一半。
`completion_effects` 只在做完时结算一次，没做完一点都没有。两种时机分在两处写，读一行就知道哪个按小时、哪个看做完。

数据集写成这样（内容行省略了与今天相同的必填字段）：

```json
{"state": "groceries", "initial": 0, "cap": 1, "reset_on_goods": ["meat-pack", "veg-pack"]}
{"content_id": "cook", "title": "做饭", "location_kinds": ["home"], "consumes_state": "groceries", "completion_effects": {"food": "meal"}, "...": "..."}
```

同一套字段还能写这些事：

| 地点里的事 | `consumes_state` | `completion_effects` |
| --- | --- | --- |
| 家里的「做饭」 | 食材状态 | `{"food": "meal"}` |
| 电影院的「看电影」 | 电影票状态 | `{"relaxation_relief": "medium"}` |
| 父母家的「吃饭」 | 不写 | `{"food": "meal", "social_relief": "high"}` |

看电影只能写在柜台买票的情形。提前在 app 上买票今天还写不出来：电影院卖的票远程下单走外卖，有骑手、运费和送达时间；
绑在 app 上的票走快递，两到五天后到驿站。这是购买履约的限制，不在本提案范围内。

<a name="proposal-grocery-cooking-人物看到什么"></a>
### 人物看到什么

- 状态为 0：家里的工具层没有「做饭」这一行。人物凭记忆照写也会被拒绝，原因写明收到哪些商品能开放它。
- 收到食材之后：人在家时工具层多出「做饭」一行，和家里其他事一样可用。人不在家时看不到家里的事，今天就是如此；
  人物靠收货记录和自己的计划记得回家做饭。
- 开始做饭：这一行不再列出，直到下一次收到食材。
- 做完：能量增加，饥饿体感随之变化，和吃了一份外卖食品一样；写了缓解档位的，放松或社交体感随之变化。

<a name="proposal-grocery-cooking-按建议定下的细节"></a>
## 按建议定下的细节

所有者只定了方向，下面这些是本文的建议；所有者没有异议就照此写进规格。

| 事项 | 建议 | 理由 |
| --- | --- | --- |
| 开放几次 | 开始时状态减 1。数据集把上限写成 1，就是「买一次做一次」；手册只教这一种写法 | 减 1 与回调的状态增量同一种语义；上限写多大是数据集的事，引擎不另设规则 |
| 什么时候用掉 | 受理开始的那一次提交里，和驿站取件同一刻；整组被拒时不扣 | 所有者原话「obsolete once the activity is called」 |
| 暂停与恢复 | 恢复不再看状态、不再扣 | 和恢复不再看营业、包裹一致；开始时已经用掉了 |
| 提前结束、运行截止 | 已扣的不退；完成效果只在内容做完时结算，没做完没有 | 效果跟着「做完」走；不按做了多久折算，按小时的部分已由原有字段负责 |
| 系列 | 同一系列各集的 `consumes_state` 必须相同；开始这个单元扣一次，系列自动接下一集不扣。`completion_effects` 各集各写，哪一集做完结算哪一集的 | 和内容前提「各集相同」一致；数据集可以把 `food` 只写在《吃晚饭》那一集 |
| 没做完的进度 | 沿用今天的规则：进度保留，下次开放时从上次的位置接着做，做完照样结算这一集的完成效果 | 上次没吃上，这次补上，总能量不会多给 |
| 状态降到阈值以下 | 照旧触发数据集写的阈值规则和提醒，例如「食材用完时盒马推送一条提醒」 | 用掉一次就是一次真实的状态变化，回调本来就比较提交前后的状态 |
| 运行开始时有没有食材 | 状态的 `initial`，数据集定 | 今天就有，不用新字段 |
| 食材本身的类别 | 数据集写 `goods`；收货时放松需要照旧减 0.10 | 所有者不要新类别；写 `snack` 或 `meal` 会在收货时补能 |
| 档位的数值 | `food` 沿用零食、食品的收货热量；两项缓解沿用按小时缓解的同名档位，一次减少的量等于这一档一小时的量 | 不新增数值，档位名在整个系统里只有一种含义 |
| `completion_effects` 能写在哪 | 任何地点内容都可以写，不要求同时写 `consumes_state` | 两件事各管一件：一个管出现与用掉，一个管做完的效果 |
| app 里的内容 | 两个字段都不能写 | 所有者选了只用于地点里的事；app 内容另有前提机制 |
| 照写一件没开放的事 | 名称照样解析到它，受理以「前提不满足」拒绝，原因列出收到哪些商品能开放；解析失败时的候选里不出现它 | 人物凭昨天的记忆写「做饭」时，「找不到这个名字」会让它以为家里没有这件事 |
| 评估里算不算一餐 | 不算。行为评估的食品种类和质量报告的利用率仍只读收货 | 做饭没有菜品身份，每晚的「做饭」算成同一件商品，会被读成天天吃同一道菜 |

<a name="proposal-grocery-cooking-不做的事"></a>
## 不做的事

- 不新增商品类别，不做库存或持有物，不按件数累计，不做配方和营养。所有者原话：「we don't do inventory system at any scale」。
- 不改食品收货：零食和食品照旧收货即吃。
- 不在 `completion_effects` 里放睡眠、资金和回调状态：睡眠只按实际睡眠结算，资金只经购买、车费和回调转账在两个账户间守恒地移动，
  回调状态的「开放、开始时用掉」由 `consumes_state` 负责，做完时改状态目前没有需要。
- 不把 `exertion` 和两项按小时缓解挪进 `completion_effects`，内容行的其余形状不变。
- 不新增目录文件，不改 `callbacks.jsonl` 和 `merchant-catalog.jsonl` 的格式。
- 不加系统层文字。能开放的事只在开放时列出，被拒时原因说清缺什么。

<a name="proposal-grocery-cooking-数据集作者要做什么"></a>
## 数据集作者要做什么

写进作者手册《设计环境数据集》，所有者已答复由手册教会数据集作者（原话「we can teach them how to achieve this in the user manual」）：

- 在 `callbacks.jsonl` 写一个状态，`initial` 写 0（运行开始时家里没菜）或 1（有菜），`cap` 写 1，`reset_on_goods` 列出全部食材商品。
- 食材商品的类别写 `goods`，照常绑定超市的地点类型或买菜 app。
- 家里做饭那条内容写 `consumes_state` 和 `"completion_effects": {"food": "meal"}`；人设的体重决定一天要吃几顿，见《编写 persona.toml》。
- 写 `food` 时避免同一顿饭算两次。例如公司里的「吃午饭」写了 `food`，人物点了外卖再去吃午饭就吃了两顿。

<a name="proposal-grocery-cooking-改动的牵连"></a>
## 改动的牵连

- **版本号。** 内容行的字段集合和引擎规则都变了：规则版本与目录格式各升一号。所有环境包要改两个版本号、刷新清单后重新发布；不用这个功能的包只改版本号。
- **已有运行不能再恢复。** 规则版本和代码身份都变了，这是预期内的。
- **提示不变。** 系统层和工具说明一字不改，两个提示指纹不变；不用这个功能的环境包里人物读到的提示逐字节相同。
- **两份完整日基线重新冻结。** 测试夹具不用这两个字段，行为不变，但生产源码变了，按既定办法重冻。
- **另一份提案。** 《首次真实模型单日运行》待裁决清单里「地点里做的事能不能解饿」一行与 `completion_effects.food` 是同一件事；两份提案的裁决要一致。
