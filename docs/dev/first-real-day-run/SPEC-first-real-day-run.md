## 改后人物这一天有什么不同

用那次真实运行里的几个时刻来看。左边是当时发生的事，右边是照本规格实施之后同一件事会怎样。

| 时刻 | 那次运行里 | 改后 |
| --- | --- | --- |
| 08:46 想喝咖啡 | 人物打开瑞幸咖啡看了三分钟，结果里什么也没有，没有下单，却记成点过了 | 人物提交一次购买：商品「冰美式咖啡」，`prefer` 写「瑞幸咖啡」。附近有上了瑞幸咖啡的店就从那里下单，手机上是瑞幸咖啡下单、付款、订单通知；购买结果写明实际用的 app。瑞幸咖啡这类没有内容的购物 app 不能再单独打开 |
| 11:49 点午饭 | 人物在美团外卖里看了菜单，订单却被抽到淘宝闪购 | 不知道吃什么时先查询「食品」，`prefer` 写「美团外卖」，五到十分钟后读到每件商品从哪家店、经哪些 app、多少钱、几点到；接着购买，`prefer` 写「美团外卖」，订单就走美团外卖 |
| 18:30 做晚饭 | 系列里有《吃晚饭》一集，但人物看不到这一集、做完也不解饿，五次决策卡在「没有吃饭这个动作」 | 做完后的结果列出做过的每一集；数据集给《吃晚饭》写明供一餐后，做完这一集能量进账，工具层在做之前就标着「第 2 集供一餐」 |
| 19:52 起刷哔哩哔哩 | 那一晚九次打开哔哩哔哩，查看器里是九段互不相干的「互动」 | 引擎不变，人物仍然每条内容各收尾一次。查看器把首尾相接的几次合成一段：20:19 到 20:43 的三次是一段 24 分钟，21:23 到 21:58 的三次是一段 34 分半，九次显示成五段 |
| 19:50 再点「在家休息」 | 上次提前结束剩下的 60 秒被接着做完，留下一分钟的残段 | 「结束」就算做完，再点是从头做起；想回头接着做用「暂停」 |
| 事后看这一天 | 时间线写「互动《散步装备准备》」，读起来像人物在家准备散步装备 | 查看器、导出的时间线、检查工具和零点计划读到的句子都写「使用哔哩哔哩《散步装备准备》」；在地点做的事写「在<地点>：早上洗漱」；购买写商品和「经某 app 下单」或「到店」 |

离线测试只能证明这些规则按写的那样执行。咖啡能不能买成、人物会不会用好 `prefer` 和查询，要等实施之后再跑一次真实模型的单日运行才算数；它不是合入的条件，本规格里一律记为「未取得」。

## 所有者已答复的一项

提案对「打开一次内容 app 只看一条短内容就结束」只定了方向，具体做法留给所有者确认。规格第一稿提了三种做法（数据集给每个 app 声明使用时长、引擎固定范围、人物每次写时长），所有者 2026-10-12 的答复是三种都不用：

> 不需要改引擎，就是在viewer的地方合并或者表明都是一个app连续使用的就可以

据此，这一项不动引擎、不动环境数据集、不动工具接口和提示，只改查看器。做法见[查看器里的连续使用](spec/06-continuous-use.md)一章，要点如下：

| 事项 | 规格的写法 |
| --- | --- |
| 什么算连续 | 同一个人物、同一个 app 的两次使用首尾相接：前一次结束的那一秒后一次开始。人物收尾和重新打开不花模拟时间，所以连着刷的几条正好是这样。人物同时还在做地点里的事时，收尾之后要等下一个叫它的时刻才再决策，中间有间隔，就不算。隔了哪怕一秒、中间换了别的 app，都不算 |
| 合并 | 查看器的活动泳道把一串连续的使用画成一段，写成「使用哔哩哔哩《标题》《标题》《标题》」 |
| 标明 | 活动表仍是每次使用一行，属于同一串的各行标出这一串的起止和自己是第几段；时间线上后几次的受理行标明是接着同一次使用 |
| 不合并的地方 | 导出文件里仍是每次使用一行；导出的一天时间线、检查工具、人物读到的句子都不合并。下游若要一段连续的前台，自己把首尾相接的行合起来 |
| 没有变的 | 人物仍然每看完一条就收尾一次、再决定要不要接着看，晚上那些零碎的收尾决策不会减少；隔开的短使用（19:52、20:00、22:51 那三次）仍是各自一段 |

## 工具接口的变化

模型能调用的原生工具从十一个变成十个。没有列在下面的工具（开始槽位 1 活动的 `start_main_activity`、三个控制工具、改计划、回看任务、三个记忆工具）参数和用途都不变。

| 变化 | 今天 | 改后 | 所属的章 |
| --- | --- | --- | --- |
| `start_side_activity` 多一个参数 `prefer` | 只有 `action`、`target` 两个参数 | 三个参数都必须出现。`prefer` 是字符串或 `null`：购买时写想用来下单的 app 全名，查询时写想在哪个 app 里查，没有想法写 `null`；打开 app 时必须是 `null`，否则按参数错误退回，原文 `prefer must be null when action is interact` | 购买时写想用的 app |
| `prefer` 写得不准 | 不适用 | 不退回、不给候选，环境悄悄另选。只有多余空格、全角半角这类差别会被抹平；写成简称或不存在的名称，订单落到别的 app，人物从购买结果里看出来 | 购买时写想用的 app |
| `start_side_activity` 多一个动作 `query` | `action` 只能是 `purchase`、`interact` | 多一个 `query`：`target` 写商品全名或四个类别名（零食、食品、饮料、商品）之一，可以混写。占槽位 2，时长由环境在 300 到 600 秒之间抽，不能暂停，做完自己结束、不用收尾。人在路上或与出发同一次回复里提交会被拒 | 查询 |
| 删除工具 `query_world` | 决策过程中随时查，不花时间，可以翻页 | 没有这个工具。模型凭旧习惯调用时当场被纠正。回看任务和三个记忆工具仍然当场完成、不花时间 | 删除 query_world 与第五种活动 |
| `interact` 能写的 app 变少 | 任何内容 app 都能打开，没有内容的购物 app 打开后附带一张商品清单 | 没有登记内容的购物 app 不能再打开，写了就退回并告诉人物把它写进 `prefer`（`Write <app> in prefer of purchase or query, not in target: this app only takes orders and has no content to open.`）。有内容的 app 照常打开，只看内容，不再附带商品清单 | 打开 app 与 app 目录字段 |
| 购买的结果 | 每份商品一行，不写经哪个 app | 每行多一个 `channel`：下单 app 的全名，或「到店」 | 购买时写想用的 app |
| 查询的结果 | 不适用 | 做完时的结果里多一个 `query`：这次在哪个 app 里查的、是只列经它能买的还是列出全部途径、各行（商品、到店或外卖或快递、哪家店、能用的 app、价格、运费、预计送达、此刻可不可以下单及原因）、还有几件没列。一次最多 20 件商品。中途结束只有「没有查完」 | 查询 |
| 用 app 或在地点做事的结果 | 做完后的结果里没有内容，人物不知道看了什么 | 做完后的结果多一个 `contents`：按先后列出每条的标题、简介、时长、是否做到头 | 做完之后读到什么，提前结束算不算做完 |
| 工具层给模型列出的东西 | 列出全部内容 app 作为可打开的目标；有一组只为 `query_world` 准备的类别索引 | 多一组 `prefer_apps`：可以写进 `prefer` 的 app 全名，整次运行不变。没有内容的购物 app 只出现在这一组里。那组只为 `query_world` 准备的索引删除。地点里供一餐的事在备注里标出「供一餐」「第几集供一餐」 | 购买时写想用的 app；在地点吃的一餐 |
| 系统层的规则 | 十七条 | 二十条：改了八条，新增三条（打开 app 只是看、买东西只有购买；怎样查询；怎样才算吃了一餐）。逐字定稿在「人物读到的规则」一章 | 人物读到的规则 |
| 每次决策的输出上限 | 8,000 | 16,000 | 十条缺陷与思考额度 |

这些变化会改变工具指纹和提示指纹，已有的运行不能再恢复或重放，这是预期内的。改后模型读到的 `start_side_activity` 完整定义（参数说明的逐字定稿）在「人物读到的规则」一章。

## 环境数据集字段的变化

数据集仓库要改的只有三处，改完重新发布环境包；不改的包在新引擎上加载会被拒。人设表 `persona.toml`、运行配置 `config.toml`、地点、商品、出行方式、地图和提醒规则这几份文件的字段都不变。

| 文件 | 变化 | 不照做会怎样 | 所属的章 |
| --- | --- | --- | --- |
| `catalog/manifest.json` | `format_version` 和 `rules_version` 都从 4 改成 5 | 加载第一步被拒：`RULES_VERSION_MISMATCH` 或 `ENVIRONMENT_KIND_INVALID` | 版本、身份与基线 |
| `catalog/app-catalog.jsonl` | 每个 app 行删掉 `browse_duration_seconds`（没有内容的购物 app 不能再单独打开，这个字段没有用处了） | 留着它的行被拒：`ENVIRONMENT_KIND_INVALID`，带行号 | 打开 app 与 app 目录字段 |
| `catalog/content-catalog.jsonl` | 每条绑定地点的内容（地点里的每一件事、系列里的每一集）新增必填的 `provides_meal`，写 `true` 或 `false`；引擎不替没写的补值。绑定 app 的内容不得写这个字段 | 没写：`provides_meal is required for a location content; allowed values: true, false.`；app 内容写了：`provides_meal must not be declared on an app content.`；都带行号和内容身份 | 在地点吃的一餐 |

不是字段、但作者要跟着注意的几件事，引擎都不检查，写进作者手册：

- 人设里写「用某 app 点某类东西」时，卖这类东西的店要登记这个 app；习惯里的 app 名要和 app 目录里的名称一字不差。
- 人设里不要写「打开某购物 app 看看」这类习惯。
- app 里的内容，标题要写成一条内容的标题，不要写成一个动作。
- 提醒规则不能订阅查询这个动作，可订阅的动作仍是今天那几种。
- 人设表或配置不合格时，数组字段的拒绝原因用词由 `List` 变成 `Tuple`；作者的写法不变。

读导出的下游要知道的变化（导出结构号 6、活动种类多一个 `query`、运行回执里 token 统计的形状）列在「版本、身份与基线」一章的「交给数据集仓库和下游的事」。

## 与提案不同的地方

写规格时对着代码逐条核对，下面几处照提案的字面做不成、提案的说法不准，或者规格比提案的字面宽。这几处以本规格为准，所有者已过目。

| 事项 | 提案怎么写 | 规格怎么写，为什么 |
| --- | --- | --- |
| 查询里写错了名称 | 类别名不在四个之内按参数错误退回并列出四个允许值；商品名找不到直接拒绝 | 两者写在同一个数组里，引擎分不出写错的是类别还是商品。合成一种拒绝：找不到，原因里列出四个类别名，不给候选，不花时间。例外只有一种：写的是一个只用于下单和查询的 app 名，退回并告诉人物把它写进 `prefer` |
| 哪些记录跟着人物进入下一段 | 与出发同一次回复里开始的 app 使用，记录进入路上那一段 | 用内容 app 或在地点做事的记录，出现在这项活动仍在进行或在其中结束的每一段。原因相同（进度层只读本段之内的请求），「出发前已经在看」「到了还没看完」同样读不到，而且通勤时更常见。所有者若只要字面那一种，把规则收窄即可，那两种情形就仍然没有记录 |
| 吃过《吃晚饭》之后还饿不饿 | 差距表写「不再饿」 | 能量确实进账。但人物自己写的饭点时段内，饥饿感至少是「有点想吃」，与能量无关，买来的食品今天也是这样；时段过了才回到「不饿」。身体模型不改，所以这一幕的改善是人物知道自己吃过了，不保证当时显示「不饿」 |
| 身体记录里「结算后」重复算了收货 | 「结算后」只反映这一笔自己的增减，加一条自检 | 照做，另有两处连带。一是清醒不适带来的那一点放松需要改成对着这一笔结算后的身体计算，所以它与饮料或商品收货落在同一秒、放松需要又接近上限时，世界里的数值与今天略有不同。二是提案没有发现的一处：请求被拒时加的那一点放松需要，分录今天漏进了下一条身体记录，改成记在这次拒绝自己的结果里，否则自检不成立 |
| 加载时的序列化警告 | 来自两个字段，每次加载环境出现，还没能复现 | 已复现。涉及人设和配置里声明成数组的全部字段，十九个字段名，其中十六个在样例上出警告；触发处是新建运行时把人设表写出去的那一步，不是加载环境。照提案把声明改成元组，连带的变化是人设不合格时作者读到的拒绝原因里 `List` 变成 `Tuple` |
| 按手册敲命令起不来 | 原因是设置导入路径排在读模型身份之后 | 今天根本没有给本进程设置导入路径的代码，要新增这一步，并和配置环境变量一起挪到读模型身份之前。`validate` 的顺序核对过，不用改 |
| 规则版本 | 只提到世界状态、导出、app 目录三个格式号会动 | 规则版本也要升（4 到 5）：选店、查询、结束即做完、供一餐都是引擎的固定规则。四个号各升一次，数字见「版本、身份与基线」一章 |
| 查询那几分钟的 app | 放到前台 | 手机上确实是这个 app 在前台。导出里记成这项查询活动名下的一段 app 使用，和人物打开内容 app 是同一种记录，不新增一种「app 前台」步骤；下游按活动种类区分 |
| 思考额度管哪些调用 | 每次决策的输出上限从 8,000 提到 16,000，截断后的重试保持现状 | 上限是一个常量，截断后的那次重试、记忆整理和就寝反思也读它，所以一起变成 16,000；重试的做法不变。零点计划另有自己的 8,000，不动 |
| 运行结果里的 token 统计 | 改为从已落盘的模型响应累计 | 照做。连带两点：`result.json` 里这一项从按模型的字典变成数组，没有版本标记，读它的脚本要跟着改；恢复和重放出来的数字含从父运行继承的响应 |
| 检查工具读错字段 | 「动作已受理」显示问号、「记忆更新」显示 0 条 | 同一类的另外四处一起修；它里面专门统计 `query_world` 的子命令随 `query_world` 一起删除，寄放在其中的一个调试数字（反思重试次数）随之没有 |
| 「人物不知道实际用了哪个 app」写在几份设计文档里 | 四份 | 三份。《模拟引擎》里没有这句话，这一份是新增而不是改写 |
| 作者手册里导航那一条 | 导航 app 的前台时段恰好是出发到到达 | 照现行设计写准：出发时没有别的 app 在用、也没有正在下的单，导航就从出发那一秒起在前台；路上用别的 app 或下单时让出。送达时刻的公式今天设计文档里没有，先写进《交换引擎》，手册再引用 |

## 写规格时定下的细节

提案没有写到、由规格定下的做法里，所有者看得见的列在这里，都按「人物会遇到什么、所有者会看到什么」写。每一条的依据在所属的章里，所有者已过目。

| 主题 | 定下的做法 |
| --- | --- |
| 购买 | 记忆里和零点计划里那句「几点买了什么、付了多少」不加渠道；渠道只写在购买结果里 |
| 购买 | `prefer` 让两件商品分到两家店、多出一份运费而余额不够时，整次购买被拒，不为省钱放弃意向 |
| 购买 | 工具层商品行上的运费和预计送达仍按没有意向的路线写；写了 `prefer` 之后实际可能更晚，以购买结果为准 |
| 查询 | 营业但没上任何 app 的店也列出来，写明要到这家店才能买。人在卖这件商品的店里时，这家店的到店行总是列出，别家店照列但此刻不可下单 |
| 查询 | 同时写了商品名和一个大类别时，指名的商品不比类别展开出来的优先，可能排到 20 件之外 |
| 查询 | 人物在查询中途被叫起来时，只读到查询还在进行、计划多久。查询和主活动恰在同一秒做完时，仍要先给主活动收尾才能下单 |
| 查询 | 想在哪个 app 里查，只看这个 app 登记了卖其中至少一件，不看它的店此刻营不营业；这一点与购买的判断不同 |
| 查询 | 数据集的提醒规则不能订阅查询。提案提到提醒规则里的活动种类按四种写死，规格读成保持四种 |
| 打开 app | 把只用于下单和查询的 app 写进购买、查询的商品位置，读到的也是那句把它写进 `prefer` 的退回。写近似的名称（登记的是「美团」而写「美团外卖」）只得到找不到，不给候选 |
| 打开 app | 只在 app 里卖的快递商品不再出现在任何清单里，只在查询的答案里出现，仍可按名称购买 |
| 提前结束 | 系列被「结束」时整件事算做完，下次点名从第一集做起。办公室九小时的工作做到中午被「结束」，下午再点名是从头的九小时；中途去吃饭要用「暂停」 |
| 提前结束 | 在地点做的事提前结束后，记忆里那句结束的话不再带「（《某某》未完）」。被结束的那一集不供餐；供餐的那一集已经做完之后才结束的，这一餐不追回 |
| 供一餐 | 一餐等于收到一件食品，不花钱，不设每天次数。检查工具的「进食次数」把它算进去；食品多样性、质量报告的食品效率、提醒规则的状态重置仍只看买来的商品 |
| 显示 | 名称只从这次运行冻结的环境目录取。只把数据库一个文件拖进查看器时，所有对象名显示「名称缺失」，并提示拖入整个运行目录 |
| 显示 | 改后的时间线脚本和检查工具读不了这次改动之前的运行，包括 issue 13 那一次；查看器仍打得开。要看改后的咖啡，只能用重新发布的环境包新建一次运行 |
| 显示 | 一次购买分成几张订单时按订单分段写；系列在地点做时写「在<地点>：<系列名>《集》《集》」；查看器「上下文」画面里的动作名全部换成中文，不只是 `interact` |
| 缺陷 | 身体记录的自检在导出时做，不成立时导出不发布，不打断正在进行的运行。命令的进程配置失败时不再留下一个只有运维日志的运行目录 |
| 系统层 | 三句概括的话不加例外：「写得不准会返回候选」（查询写错名称时不给候选）、「接不了这一单时环境另选一个」（没有任何 app 卖时查询期间手机上没有 app）、「你所在的地点就卖这件商品时直接到店买」（已打烊时被拒）。系统层不承诺吃过就「不饿」 |
| 样例环境 | 仓库里的样例环境四条地点内容都写不供餐；供一餐的行为由测试在样例的副本上构造 |
| 验收 | 每条规则一条走真实请求、引擎和数据库的行为测试；每条裁决再登记一条源码变异证明测试咬得住，新登记约六十四条，变异套件大约多跑半小时。查看器的规则由它自己的行为用例守住。不加扫描字样的守卫测试 |
