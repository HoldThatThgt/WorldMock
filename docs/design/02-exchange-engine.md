## 1. 交换引擎与项目框架

<a name="exchange-engine-用户的心智模型"></a>
### 用户的心智模型

> “资源引擎和交换引擎应该是相对静态的引擎”
>
> “这里是心智模型文档”
>
> “把引擎的职责边界确定好，不要写一些不属于我们引擎范围的东西”

交换引擎回答：在给定条件下，这件事能不能做，需要付出什么，能够得到什么。
例如，购买食品要满足哪些条件、需要支付多少、能够取得多少食品，以及何种条件下才能交付。
这些规则需要先登记，并随资源、对象和语料的新增、修改、删除一起维护，供运行时查询。
交换引擎把判断和计算结果交给模拟引擎，由模拟引擎决定何时调用并落实变化。

<a name="exchange-engine-项目框架映射"></a>
### 项目框架映射

```mermaid
flowchart LR
    C[环境目录：对象与绑定] --> R[资源引擎：登记与只读查询]
    X[交换引擎：固定类型与常数] --> V[条件与资源变化求值]
    R --> V
    S[模拟引擎：当前事实与活动] --> V
    V --> S
    S --> F[记录引擎：实际提交与数字足迹]
```

规则维护通过 WorldMock 的源码、测试和 `RULES_VERSION` 发布完成。环境发布不能新增公式或覆盖常数；纯计算和目录查询不自行推进时间或制造事实。

<a name="exchange-engine-与其他引擎的职责边界"></a>
### 与其他引擎的职责边界

| 负责方 | 职责 | 衔接 |
| --- | --- | --- |
| 资源引擎 | 登记、校验对象与绑定，派生只读索引 | 提供已校验的目录事实 |
| 交换引擎 | 固定类型、常数、纯条件与投入产出求值 | 返回可应用变化或拒绝原因 |
| 模拟引擎 | 共享时钟、活动推进、身体演化与原子世界变化 | 按真实活动应用规则结果 |
| 记录引擎 | 状态、事件、检查点与实际足迹 | 保存已提交事实与身份 |

资源定义归交换引擎，具体世界来源和发布归 Dataset。

<a name="exchange-engine-系统固定类型与常数"></a>
## 系统固定类型与常数

`worldmock.exchange` 是系统类型、资源定义、身体常数与交换公式的唯一定义处。`types.py` 声明地点、食品、内容与摘要来源闭集，`constants.py` 声明版本与常数，`operators.py` 用 Decimal 求值，`body.py` 定义身体演化常数；全部由 `RULES_VERSION = 1` 绑定。

| 内容 | 规则 |
| --- | --- |
| 地点与活动环境 | 八个 `LocationKind`；`PLACE_KIND_ENVIRONMENTS` 派生生活活动环境 |
| 食品 | 零食 200 千卡/300 秒、饮品 100 千卡/180 秒、正餐 600 千卡/1200 秒，每份固定 |
| 出行 | 步行 1.2 米/秒、驾车 7 米/秒；时长按图距离向上取整，驾车费用 `max(500, ceil(0.2 × 米))` 分，步行零费 |
| 配送 | 5 米/秒、备餐 600 秒、配送费 500 分/单 |
| 图生成 | 至少两个节点，边长 200–2000 米，种子驱动规范生成器；生成规则版本 1 |
| 身体 | `BODY_CONSTANTS`，800/400 千卡阈值，既有食品利用效率与能量上限保留 |
| 资源分录 | 购买转账、食品摄入、出行费用与资金守恒仍由纯算子求值，模拟引擎应用实际变化 |

环境只登记对象和绑定，不提供品类树、配方、算子、公式或资源定义。三份既有包 TOML 的逐字节副本机制不变。实际图出行、购买、app 与工作消费者分别在后续阶段闭合，不能把本节常数已定义当作完整运行已通过。

<a name="exchange-engine-交换对象与资源变化声明"></a>
#### 交换对象与资源变化声明

交换对象来自已登记 `Catalog`：食品提供类别、价格与店铺绑定，地点提供类型与 app 绑定，内容和工作主题提供具体世界材料。资源定义与公式来自 `worldmock.exchange`；环境不能覆盖食品热量、出行或配送常数。
输入为当前事实、对象与数量；输出为拒绝原因或本次资源变化。模拟引擎负责原子提交，纯求值不推进时钟、不写状态。

<a name="exchange-engine-可供性与活动声明"></a>
#### 可供性与活动声明

固定活动闭集与占用声明仍读取包内 `affordances.toml`；环境副本必须逐字节一致。地点资格从 `LocationKind` 经 `PLACE_KIND_ENVIRONMENTS` 派生，生活活动条目保留自己的 `location_kinds` 和效果。
本阶段保持当前十一项占用名；app 活动与八项占用名在阶段 4 同时切换，不由环境新增活动或更改占用。身体常数从 `worldmock.exchange.body` 读取。

#### 交换规则的加载与准入



<a name="exchange-engine-校验交换条件"></a>
### 校验交换条件

校验只读取当下人物位置、持有、余额、活动占用与 `Catalog` 绑定，以及 `worldmock.exchange` 闭集常数。食品店铺全天服务，没有营业时态、报价、资格或库存；食品是否能买由店铺菜单、app 绑定、方式和余额决定。
多项请求仍先完成全项准入再提交一笔变化，拒绝不能制造扣款或交付事实。购买消费者在阶段 3 接入，登记校验在阶段 1 即拒绝未知引用、非食品地点绑定和同类不同菜单。

<a name="exchange-engine-门店供给的时态与履约判断"></a>
### 门店供给的时态与履约判断

店铺全天服务。食品的唯一价格在 `foods.json.price_fen`，菜单从 `store_ids` 或 `"all"` 派生；没有供给时态、营业例外、报价、有效期或库存。
到店与配送是否受理读取地点、店铺 app 绑定、收货人和当前位置。配送费用与时长常数归 `worldmock.exchange`，实际订单与到货幂等在阶段 3 验证。

<a name="exchange-engine-计算投入产出"></a>
### 计算投入产出

**目的：计算给定条件下的资源变化。** 输入是适用规则、数量和模拟引擎提供的实际履约事实；
输出是投入、产出及相应的付款、使用或交付条件。

<a name="exchange-engine-资源变化的计算"></a>
#### 资源变化的计算

购买按食品价格、份数和固定配送费计算，驾车按图距离与固定费率向上取整；同一笔货款与配送费付给 `merchant:<store_id>`，车费付给 `transport:service`。食品摄入按类别固定每份热量与实际吃掉份量求值，再由身体模型应用利用效率。
所有常数只从 `worldmock.exchange` 读取；计算不自行写余额、持有或足迹。真实消费、出行和购买分别随所属实施阶段验证。

<a name="exchange-engine-不同交换的计算依据"></a>
#### 不同交换的计算依据

| 交换 | 输入事实 | 唯一规则来源 |
| --- | --- | --- |
| 购买 | 食品统一价格、份数、履约方式 | `exchange.operators` 与配送费常数 |
| 进食 | 食品类别、实际摄入份数、睡眠不足 | `FOOD_CONSTANTS` 与 `BODY_CONSTANTS.food_efficiency_curve` |
| 出行 | 图距离、步行或驾车方式 | 速度和车费常数；图查询阶段 2 接入 |
| 工作 | 主题与实际工作秒数 | 主题进度阶段 5 接入；不登记计时计件或工作包公式 |

运行状态和实际履约由模拟引擎提供；目录不保存另一份交换规则。

<a name="exchange-engine-校验资源分录"></a>
### 校验资源分录

资源分录继续校验单位、有限数值、上下界和封闭资金守恒。资源定义从 `worldmock.exchange` 取得，不能从环境 `resources.jsonl` 加载；计算错误保留稳定英文错误和异常日志。
通过求值的分录只是候选变化，只有模拟引擎实际提交后才成为可追溯的数字足迹。

<a name="exchange-engine-返回规则结果"></a>
### 返回规则结果

**目的：把本次判断、计算与校验的结果交给模拟引擎。**
结果要清楚区分“允许执行”和“根据已发生事实算出的变化”，不能把预计产出描述为完成结果。
全部接口拒绝给出英文说明，`items[]` 每项包含
`path/written/error_code/allowed_values/expected/why/candidates`；`path` 从模型工具调用根开始，保留全部数组下标，
`why` 写参数、名称或世界前置条件的英文原因。不以笼统失败代替参数诊断，不采用旧 `index/field` 形状。
可照填候选只用完整 `{tool, arguments, note}` 调用。
`query_world(name, way, category, from, available_only, offset)` 读取同一冻结权限下的固定食品菜单与价格；category 来自公开可调用索引，
`from` 与购买请求用同一个来源解析函数（登记店铺显示名或 app 名，只匹配食品条目），`available_only` 只读取冻结观察里已求得的动作与工具
`available`，不重新求值交换条件，成功仍以受理时的重验为准；以 matches/total_count/next_offset 返回可遍历的每页结果，逐项不再附候选，
不触发交换求值副作用或呈现留痕。

| 结果内容 | 应表达什么 |
| --- | --- |
| 条件判定 | 当前动作或交换是否满足要求 |
| 变化明细 | 哪一方的什么资源应增加或减少多少，以及计算所依据的事实 |
| 履约条件 | 取得、使用、付款或交付还需满足什么条件 |
| 拒绝原因 | 哪个条件或资源约束不满足，不能用替代行动冒充成功 |

模拟引擎消费这些结果，负责执行、安排履约和更新状态。交换引擎没有独立的世界状态，
也不负责事件排队、时间推进或记录保存。

食品结算结果以固定价格、类别热量、配送费与真实数量为依据；没有独立交换规则 JSON、供给报价或库存结果。实际付款、交付与消费由模拟引擎分别提交。

<a name="exchange-engine-食品交换的规则调用"></a>
#### 食品交换的规则调用

目录登记食品类别、统一价格和店铺绑定；纯规则从类别取得每份热量和完整食用时长。购买后形成真实订单，送达后增加相应地点持有；开始吃时冻结实际份数，结束结算实际摄入与丢弃。
该链的实际调用和恢复幂等在阶段 3 接入并验证；阶段 1 已实现严格登记、常数求值与环境命令，不宣称完整食品活动已通过。

## 3. 当前实现与验收

<a name="exchange-engine-实现职责与证据入口"></a>
### 实现职责与证据入口

固定类型和常数在 `src/worldmock/exchange/`，环境登记在 `src/worldmock/catalog/`，命令入口为 `worldmock environment generate-map` 与 `worldmock validate --environment`。冻结规格的验收台账登记实际生产符号、行为节点与变异；环境命令校验通过和完整引擎行为通过分别记录。
后续阶段按图出行、食品、app、工作、足迹、交付和完整日顺序闭合真实调用，不以常数单测代替运行证据。

<a name="exchange-engine-当前差距"></a>
### 当前差距

阶段 1 提供固定规则、七份环境目录、统一登记、地图发布命令和纯加载边界。完整引擎消费新环境需等待图出行、购买、app 和工作消费者共同完成，最小运行闭环在阶段 5 验证。
目录中不保留待扩展的规则注册、占位图查询、品类维护或旧格式兼容入口。

<a name="exchange-engine-分阶段验证与完成条件"></a>
### 分阶段验证与完成条件

先验证固定常数、严格环境登记和真实 `generate-map/check/validate --environment` 命令；随后以实际引擎调用验证图出行、购买、app 接触和工作主题，再核对足迹、恢复、导出与交付。
每个阶段只登记已经存在的生产符号、具名行为节点和有效 SourceMutation。阶段 5 的最小端到端与阶段 8 的完整自然日分别提供运行闭合证据；文档冻结与目录有效不等于运行完成。

<a name="design-exchange-engine-current-responsibility"></a>
## 纯规则与执行职责

交换引擎拥有固定闭集、常数、Decimal 算子与资源分录规则；环境只登记对象与绑定。系统规则由 `RULES_VERSION` 统一绑定，恢复核对五字段 `environment_identity`。历史品类契约只保留归档原文与执行证据，不再作为现行规则入口。
