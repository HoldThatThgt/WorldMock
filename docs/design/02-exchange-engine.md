<a name="exchange-engine-交换引擎与项目框架"></a>
## 1. 交换引擎与项目框架

<a name="exchange-engine-用户的心智模型"></a>
### 用户的心智模型

> “资源引擎和交换引擎应该是相对静态的引擎”
>
> “这里是心智模型文档”
>
> “把引擎的职责边界确定好，不要写一些不属于我们引擎范围的东西”

交换引擎回答：在给定条件下，这件事能不能做，需要付出什么，能够得到什么。
例如，购买食品要满足哪些条件、需要支付多少、能够取得多少食品，以及何种条件下才能交付。
这些规则需要先登记，并随资源、对象和语料的新增、修改、删除一起维护，供运行时查询。
交换引擎把判断和计算结果交给模拟引擎，由模拟引擎决定何时调用并落实变化。

<a name="exchange-engine-项目框架映射"></a>
### 项目框架映射

    R -->|已发布的定义与属性| D
    E[维护者：新增、修改或删除声明] --> M
    A[数字人：选择行动] --> S[模拟引擎：提供当前事实并落实结果]
    S -->|动作、目标、当前条件与实际履约事实| D
    subgraph X[交换引擎]

        V[校验交换条件<br/>资格、地点、占用、余额、库存与履约状态]

        O[返回规则结果<br/>条件判定、变化明细、履约条件或拒绝原因]

图中同时展开规则维护和运行时调用；规则维护不是每次交换都要执行的步骤。
当前能力由多个模块共同承载，维护流程的缺口见[当前差距](02-exchange-engine.md#exchange-engine-当前差距)。一次查询或计算不会自行推进时间，
计算结果也不等于世界已经发生变化；模拟引擎负责把结果应用到运行中的世界。

<a name="exchange-engine-与其他引擎的职责边界"></a>
### 与其他引擎的职责边界

| 负责方 | 负责什么 | 与交换引擎如何衔接 |
| --- | --- | --- |
| [资源引擎](03-resource-engine.md#resource-engine-worldmock-产品设计说明书-资源引擎) | 定义资源与对象，维护内容、来源、版本、检索与提供 | 提供规则所需的定义和属性 |
| 交换引擎 | 维护交换规则及其引用关系，查询规则、判断条件、计算投入产出、校验本次资源变化并返回结果 | 登记并校验规则；运行时接收事实，返回判断与计算结果 |
| [模拟引擎](04-simulation-engine.md#simulation-engine-worldmock-产品设计说明书-模拟引擎) | 时间与事件调度、活动推进、身体演化、效率求值、验收调用和世界状态更新 | 提供实际时长、工作量、身体计算结果与履约事实，按交换规则执行 |
| [记录引擎](05-recording-engine.md#recording-engine-worldmock-产品设计说明书-记录引擎) | 状态与足迹持久化、历史核验、检查点与恢复 | 接收模拟引擎实际提交的状态和证据 |

正文按图中的功能展开。身体模型、活动生命周期、共享时钟和预排事件由模拟引擎设计承载；
存储事务和历史审计由记录引擎设计承载。交换引擎只说明与这些能力之间的输入输出关系。

<a name="exchange-engine-交换引擎的功能设计"></a>
## 2. 交换引擎的功能设计

先说明规则如何登记和维护，再用“购买一份食品，送达后再进食”说明运行时如何使用规则。
每次运行时调用只处理模拟引擎提供的当下事实。

<a name="exchange-engine-维护交换规则"></a>
### 维护交换规则

**目的：让新增、修改或删除的资源、对象与语料，具有一致且可用的交换规则。**
输入是待变更的声明及其引用关系；输出是通过检查、可供发布的规则，或需要处理的缺失与冲突。
品类、属性继承、三态配对和闭集算子的冻结行为见[品类契约规格](../dev/SPEC-category-contract.md#spec-category-contract-品类契约与交换规则开发规格)。
下文说明职责，实际实施证据见[品类契约验证台账](../dev/category-contract-verification.md)。

<a name="exchange-engine-注册表登记什么"></a>
#### 注册表登记什么

注册表把“有什么”和“允许怎样使用、会产生什么变化”关联起来。
它由资源定义、对象、语料引用和规则声明组成，按标识相互引用；不要求把所有内容存进同一种对象结构。

| 登记内容 | 例子 | 维护职责 |
| --- | --- | --- |
| 资源定义 | 能量的单位、范围与归属 | 资源引擎维护定义；交换引擎的规则引用它 |
| 对象与语料条目 | 一种食品的属性、一部影片的素材和元数据 | 资源引擎维护身份、内容、来源与版本 |
| 使用方式与交换规则 | 食品允许购买和进食；观看影片需要哪些条件、按什么依据计算效果 | 交换引擎维护条件、投入产出与履约要求 |

某个人此刻还剩多少能量、持有几份食品、影片看到了哪里，是模拟引擎维护的运行状态。
新增资源定义不会自动给每个人创建状态，删除语料条目也不等于删除人物已经发生的观看记录。

<a name="exchange-engine-新增状态资源对象或语料"></a>
#### 新增状态资源、对象或语料

```mermaid
flowchart TB
    A[新增或修改资源、对象、语料] --> R[资源引擎：登记定义、内容与引用]
    R --> M[交换引擎：关联使用方式、条件与投入产出规则]
    M --> C{引用完整，规则一致<br/>相应能力已经支持？}
    C -->|否| F[列出缺失或冲突，补齐后重新检查]
    C -->|是| P[资源引擎：发布固定版本的目录与语料]
    P --> S[模拟引擎：选择版本并初始化运行]
    S --> Q[运行时查询适用规则]
```

| 维护场景 | 资源引擎登记什么 | 交换引擎维护什么 | 何时可以使用 |
| --- | --- | --- | --- |
| 新增一种状态资源，例如水分 | 单位、归属、上下界与来源 | 哪些交换输入或消耗水分、使用什么条件与计算依据 | 模拟引擎已支持该状态的初始化、变化与应用，相关规则经调用验证 |
| 新增商品、服务或合同 | 身份、属性、规格与来源 | 支持的动作、资格、占用、投入产出和履约要求 | 定义与规则引用完整，相应交换计算和执行能力已支持 |
| 新增一部影片等已有类型的语料 | 素材、元数据、来源、文件身份与内容引用 | 关联已有的观看规则；只有使用条件或效果依据不同时才需要调整规则 | 素材可读取，场景可引用，相应活动已支持 |

新增同类条目通常复用已有规则，不为每部影片或每种食品重复发明一套规则。
新增内容类型或新的交换方式则需要相应的读取、判断、计算与执行能力；登记本身不能补出这些能力。
身体持续变化的算法仍由模拟引擎设计承载，本节只要求新增状态能够被实际使用。

<a name="exchange-engine-修改与删除"></a>
#### 修改与删除

修改条目时，检查引用它的交换规则是否仍然成立，再由资源引擎发布新的固定版本。
例如食品份量变化后，应重新核对进食数量与能量输入，门店供给另行声明其报价；只改展示信息不能视为规则已经同步。

```mermaid
flowchart LR
    A[提出删除资源、对象或语料条目] --> B[查找引用它的规则、对象与场景]
    B --> C[明确修改或移除受影响的引用]
    C --> D{待发布版本仍有失效引用？}
    D -->|有| E[拒绝发布并列出引用来源]
    D -->|无| F[发布移除后的目录与语料版本]
```

删除面向待发布的版本：该条目退出可用集合，规则和场景不能继续引用它。
交换引擎处理交换规则中的关联；资源引擎处理定义、素材及内容引用；场景引用由场景维护者处理。
例如删除影片时，要移除针对该影片的关联，但其他影片仍可使用通用观看规则。
删除状态资源时，则需要同时处理使用它的规则与模拟能力；不能只删注册条目而留下仍会读写它的活动。

已经开始的运行继续使用其绑定的固定版本；新版本的发布不直接修改运行中的世界。
历史运行所需的固定材料由资源引擎保留，实际使用证据由记录引擎保存；素材文件清理由资源引擎处理。
当前目录的退役操作保留条目并拒绝新引用，它与彻底删除文件不同，也尚未覆盖语料删除的完整流程。

定义与实例分离参考 [Unity 的共享数据资产](https://docs.unity3d.com/6000.1/Documentation/Manual/class-ScriptableObject.html)；
变更前查询引用关系参考 [Confluent 注册表的引用查询](https://docs.confluent.io/platform/current/schema-registry/develop/api.html#list-schemas-referencing-a-schema)。
本项目继续使用已有目录、语料清单和声明文件承载这些关系。

<a name="exchange-engine-查询适用规则"></a>
### 查询适用规则

**目的：确定这次动作按什么规则处理。** 输入是动作、目标对象、场景指定的规则版本和必要的当前条件；
输出是适用的交换条件、计算依据与履约要求。

```mermaid
flowchart LR
    A[动作与目标] --> B[解析对象品类与继承属性]
    B --> C[查询有向配对的唯一最具体声明]
    C --> D{配对状态}
    D -->|已定义| E[执行闭集算子并校验资源约束]
    D -->|已验证不作用| F[拒绝动作且不改变业务状态]
    D -->|未定义或歧义| G[场景准入拒绝]
```

<a name="exchange-engine-交换对象与资源变化声明"></a>
#### 交换对象与资源变化声明

| 查询什么 | 需要得到什么 | 食品例子 |
| --- | --- | --- |
| 门店供给 | 地点、商品、卖方、当前报价、库存与履约条件 | 从哪家门店购买、向谁付款、怎样交付 |
| 商品、服务或合同 | 商品规格与使用效果、服务或报酬依据 | 食品每份提供什么，工作按什么合同结算 |
| 活动声明 | 支持的动作、占用要求、使用条件与效果依据 | 购买与进食分别适用什么条件 |
| 资源定义 | 各资源的单位、取值边界与守恒要求 | 钱以分计，食品以份量计，能量以 kcal 计 |
| 资源变化声明 | 何种行为产生何种投入与产出，涉及哪些主体 | 购买产生付款义务，实际进食产生食品消耗；给予只转移持有物，不产生付款或摄入 |

资源和对象定义由资源引擎提供；交换引擎解释其中与当前动作有关的规则。
交换双方、当前位置、有效报价和已持有数量由模拟引擎提供，不由规则查询自行创造。

<a name="exchange-engine-可供性与活动声明"></a>
#### 可供性与活动声明

活动声明说明一个对象允许怎样使用，以及这种使用需要满足什么条件、可能产生什么效果。
交换引擎读取其中的交换条件与计算依据，例如食品的使用方式、所需份量和热量，
或工作的资格、验收要求与付款方式。

同一活动应使用一致的条件和效果规则。对象如何被检索、怎样向数字人呈现，见资源引擎；
数字人何时行动、活动如何推进，见模拟引擎。

活动声明同时明确占用 `idle`、`travel`、`eyes`、`ears`、`hands`、`voice` 或 `work` 中的资源。
交换条件对每一启动项重算地点（出行中为「途中」）、资格、目标与占用；模拟引擎对原子组合在同一暂存世界重算全部条件。
同时两条出行、途中到店取得一律拒绝；能量不参与交换条件。每人两个活动名额，进行中、暂停中与待收尾的活动各占一个。
没有声明的资源不占用，暂停和终态释放占用，不能用隐藏的全局位置锁或组合白名单替代声明。声明表及允许组合见[一日行为可信性规格](../dev/SPEC-dayrun-behavior.md#spec-dayrun-behavior-唯一状态与资源准入)。

<a name="exchange-engine-交换规则的加载与准入"></a>
#### 交换规则的加载与准入

规则可用的前提是所引用的资源与对象存在、计量单位一致、交换双方明确，且条件与计算依据不矛盾。
资源引擎负责定义的来源、版本和发布；交换引擎检查这些定义能否共同表达当前交换。

**食品例子：** 购买时查询付款与交付规则；进食时查询使用条件、份量与食品输入规则。
同一食品对应不同动作，适用的投入产出不同。

<a name="exchange-engine-校验交换条件"></a>
### 校验交换条件

**目的：判断给定事实是否满足交换要求。** 输入是适用规则、请求与当前条件；
输出是条件满足，或具体的拒绝原因。

| 校验内容 | 要回答的问题 | 食品例子 |
| --- | --- | --- |
| 动作与目标 | 是否允许对这个目标执行这个动作？ | 可购买的商品是否也支持进食 |
| 资格与地点 | 使用者是否有资格，所在位置（出行中为「途中」）是否满足要求？ | 食品是否在当前可以使用的地点；途中没有可用的持有物；给予要求与收件人同处（同世界人物在同一地点，联系人则本人位于其收货地点） |
| 来源与去向 | from是否真实持有或可以取得，to=null是否指本人、实名是否指可接收的其他人物或联系人？ | 进食与给予的来源由from=null映射到本人手边持有物；购买from=null为不约束门店、地点显示名（含「家」「住处」）限定该地点、渠道称呼限定成员门店；to=null为本人，旧“自己”字符串拒绝；收货人没有收货地点时不能收实物 |
| 余额与库存 | 金额和数量是否足够？ | 购买看余额与所选供给库存，进食与给予看手边持有数量；不足一份也可以消费，份量取实际持有 |
| 时长与并行 | 派生时长是否合法，所需占用与活动名额是否可用？观看、游戏内容与生活活动超过派生时长上限时按上限受理，出行超限拒绝；上限见[模拟引擎](04-simulation-engine.md#simulation-engine-校验与占用安排) | 进食时长越界即拒绝，不取上限，不足一份时按份量折算且不少于 60 秒；给予是瞬时动作，不占名额；占用与名额是否满足条件 |
| 履约状态 | 是否到期、已交付、已验收或已付款？ | 配送未完成时不能按已持有食品处理 |
| 报价与规则依据 | 请求依赖的报价等条件是否仍有效？ | 改价后不能按失效报价付款 |

能量不是交换条件，预计成本只用于结算与预测，计算本身不会发生消耗。
模拟引擎在需要受理或落实变化时提供当下事实，交换引擎据此重新校验；曾经可行不保证现在仍然可行。
实际偏好影响数字人如何选择，不能替代余额、库存和使用资格等事实条件。

**食品例子：** 钱足够时可以通过购买校验；食品尚未送达时，进食校验仍应拒绝。
如果一张订单中有任一商品不满足条件，整单拒绝，不自动删减商品；指名购买分段解析出的问题（商品找不到、`from` 不是门店或渠道、标签的门店
不在 `from` 的范围里、那家店不卖、不支持所写方式，以及此刻服务不了）逐项写进拒绝的 `items[]`，每项带从模型工具调用根开始的完整位置数组 `path`、人物所写的
原文 `written`、该项的 `error_code`、合法值 `allowed_values`、约束 `expected`、英文原因 `why` 与至多 3 个完整 `{tool, arguments, note}` 候选 `candidates`；顶层码取第一个名称类问题的码，都不是名称类时为 `ACTIVITY_PRECONDITION_UNMET`，其余条件报
第一条，整组仍原子受理（[一日运行保真规格](../dev/SPEC-as2-integration.md#dayrun-fidelity-错误合同)第四章、3.2、3.5）。多家门店都能服务不是问题，
按下节的请求级 `prefer` 选定一家。

<a name="exchange-engine-门店供给的时态与履约判断"></a>
### 门店供给的时态与履约判断

购买以 `supply_id` 查询地点、商品和卖方，当前报价及库存由模拟引擎提供。
商品不携带门店价格或静态购买转账边；同商品的供给彼此独立，已取得商品仍共享规格和消费效果。
品类购买配对与 `RuleEdge` 保留，规则读取模拟引擎提供的有效供给报价，不声明作为实际报价使用的商品价格槽。
对象有效属性中的 `purchase_price_fen_min/purchase_price_fen_max` 只给离线构建定义同币种的正整数分范围，
允许相等；构建对 `[random_seed, location_id, object_id]` 使用
`json.dumps(..., ensure_ascii=False, separators=(',', ':'))` 后编码为 UTF-8，取 SHA-256 摘要的无符号大端整数 `h`，
逐店 `price_position_percent` 为有来源的整数 5 至 95，固定 `jitter = h % 11 - 5`，
以 `min + ((max - min) * (price_position_percent + jitter) + 50) // 100` 生成一次初始报价，
冻结为该门店的独立 `QuoteConfig`，不为每商品独立抽整个范围，不新增扰动配置。
本正式地图中的门店按同一地区比较，所有便利店定位至少高于地图内普通超市 10 个百分点，
同商品报价不得更低，舍入同价合法；不新增地区字段。
这只是有来源的正式场景假设，其他门店定位仍按事实或明确假设声明。
交换引擎不抽价，观察、查询、结算与恢复不重抽；它只求值当前有效报价，范围、来源和所有调价越界由准入共同校验。
每个订单行调用 `evaluate_purchase(quote.price_fen, quantity, coefficient)`，以 Decimal 对整行乘积向上取整分，形成该行的 `total_price_fen`；整单 `total_price_fen` 为各行金额之和。不得先对单价取整再乘数量。
报价声明不因系数求值改变；实际收款账户取供给卖方。
公开供给行保留原始 `price_fen`、`price_version` 与 `quote`，同时提供 `purchase_pairing_state`、`purchase_coefficient` 和 `purchase_price_fen`。
配对为 `defined` 时，系数来自冻结声明，`purchase_price_fen` 通过同一 `purchase_amount` 入口计算购买一份的实际金额；报价未知时金额为 `null`。
配对不是 `defined` 时保留原始报价和配对状态，系数及实际金额均为 `null`，`purchase_allowed=false`；动机跳过该供给，但不隐藏已持有物品。
人物的余额判断和价格排序也使用该入口计算的一份金额。多份请求必须用原始报价、数量和系数重新求整行金额，不能把已取整的一份金额乘以数量。
原始报价保持正整数分；明确的 `defined` 配对可以有零系数并产生零额付款，仍正常扣供给库存和履约，不能把 `no_effect` 当作零价购买。

| 判断 | 规则 |
| --- | --- |
| 营业与访问 | 分钟级周区间、跨午夜、日期例外与世界覆盖使用统一解释；结果是开放、关闭或未知，缺资料不开放；到达重新验证访问资格 |
| 报价 | 半开生效区间，不重叠；未生效和间隙无报价；购买必须提交当前报价版本，不能自动换价 |
| 整单 | 一至五个不同供给，同地点同卖方；任一条件失败，账户、供给库存、订单与持有物均不变化 |
| 自提 | 人物和目的地都为所选门店；不额外要求配送路线；送给别人时收货人也须在店里，否则为「暂时送不到<名>那里」（`unmet` 为 `delivery_destination`） |
| 配送 | 供给支持方式和目的地范围、冻结运输路线可达；目的地为收货人的收货地点（自己为当前地点，同世界人物为其所在地点，联系人为其收货地点）；按最迟备货时刻加分时运输时长一次配送；「送达地不在配送范围」与「门店到送达地的配送路线缺失（没有、不可达或未知）」是两个原因（`ACTIVITY_PRECONDITION_UNMET` 的 `unmet` 分别为 `delivery_destination`、`delivery_route`，各一句）：送给自己时说「这里」，准入与整单结算用同一条配送道路判定，下一步只指向能送达且此地可达的地点；送给别人时同样分两句，「这里」换成「<名>那里」，下一步是先送到自己这里再当面给，收货人此刻没有收货地点（联系人没有收货地点、同世界人物在途中）时为「暂时送不到<名>那里」；指名购买有几家出售门店而都送不到时合成一句「出售它的门店都送不到<收货地>」（一日运行保真规格 5.3）；配送来源可以是购买渠道的成员门店：`from` 写 App 称呼时只在该渠道的成员门店里解析，渠道不带交付语义，送达仍按选定门店的备货与冻结路线，订单另记 `channel_id`（一日运行保真规格 3.3） |
| 交付与使用 | 付款不产生已持有物品；持有人按to映射，null为本人、实名为其他人物；订单只有一个收货人，交付到目的地后只入收货人的持有，方可使用；取得后仍按商品身份合并数量；直接送给他人与自己收货后再给予不会重复转移 |

环境不替人物换成别的商品。人物可以把挑店交给系统：只写商品名，`from` 写 null 或渠道称呼；方式写「购买」时连到店还是远程下单也由系统定
（人在出售它的门店里、东西在那里交得到收货人手上——收货人是自己，或此刻也在那家店里——就到店，否则能送到收货地就远程下单；系统不定
一个交不到收货人手上的方式，两者都不行时下一步只指向能到店买的出售门店，送给别人时是先送到自己这里再当面给）。多家都能服务时不论
`from` 是 null、地点显示名还是渠道称呼，都按请求级 `prefer`
选定一家：“最快拿到”远程下单取预计送达最早、到店取从当前地点出发路线最短，“到手价最低”取到手价最低，并列时先比到手价、
再比门店标识；选定只看能否服务，不看营业与库存（整单结算照常检查），所选的完整标签与「购买」定下的方式写进受理结果 `details.notes`，
不以 `SUPPLY_NAME_AMBIGUOUS` 拒绝（一日运行保真规格 3.3、3.5）。此外环境不依据品牌、价格或距离替人物选择。
含到店、远程下单或购买项时prefer必须为上述两个中文值之一，不含购买项时必须为null；null不默认最快，旧英文值拒绝。
购买项to=null为本人，其他收货人写实名；“自己”字符串拒绝。条件失效只拒绝本次购买，已经发生的旅行与费用仍是事实。
时态字段和错误区分见 [地图与门店供给合同](../CONTRACTS.md#contracts-地图与门店供给合同)。

<a name="exchange-engine-计算投入产出"></a>
### 计算投入产出

**目的：计算给定条件下的资源变化。** 输入是适用规则、数量和模拟引擎提供的实际履约事实；
输出是投入、产出及相应的付款、使用或交付条件。

<a name="exchange-engine-资源变化的计算"></a>
#### 资源变化的计算

| 变化类型 | 含义 | 例子 |
| --- | --- | --- |
| 转移 | 一方减少，另一方增加同种资源 | 买方付款，商家收款；给予把物品从本人手边移入对方持有 |
| 产生 | 按有来源的输入增加资源 | 食品输入对应的能量增加 |
| 消耗 | 按实际用量减少资源 | 吃掉的食品份量 |
| 转换 | 按规则原子改变输入与输出库存 | 制作完整结束后，将真实食材包转为明确绑定的可食用正餐；制作本身不摄入热量 |

各资源分别计量和校验，金钱、时间与能量不能相加求守恒。
身体计算结果、实际活动区间和有效工作量都是模拟引擎提供的输入；交换引擎使用这些事实求值规则。
用于受理的预计投入（能量除外）与用于结算的实际投入必须区分，计划尚未执行的部分不能计入实际产出。

<a name="exchange-engine-不同交换的计算依据"></a>
#### 不同交换的计算依据

| 交换 | 接收的事实 | 返回的计算结果与条件 |
| --- | --- | --- |
| 购买 | 当前有效报价、数量、交换双方与交付方式 | 整单金额、取得数量、交付条件 |
| 进食 | 开吃份量、实际消耗份量、食品属性与适用的食品利用效率 | 食品消耗与对应能量输入；不把购买本身算作进食；暂停保留开吃份量的剩余，结束丢弃未吃的部分，不补算摄入，其他份数不动 |
| 给予 | 本人手边的持有量、收件人与是否同处 | 每件转移 min(1, 持有) 到对方持有；不产生付款，任何人都不增加摄入 |
| 工作 | 合同、实际投入、有效工作量、验收结果与付款记录 | 满足合同条件时的报酬；已付款任务不重复计款 |
| 出行 | 路线、方式、适用时段与报价依据 | 应付费用与取消条件；现行规则为启程预付一次，取消不退 |
| 内容使用 | 实际接触的内容、口味权重、接触次数与时长；接触次数只在首次与从头重看时加一，接着看不加 | 本次内容体验对应的需要缓解量：内容费率 × 有效偏好 `f + (1 − f)·w` ÷ 接触次数，`f` 为场景下限偏好（缺省 0.5），不喜欢的内容也按 `f` 缓解；游戏同一算法：口味权重与内容一样按题材计算（没有题材声明的为零，按 `f` 缓解），缓解量为目录费率 × 有效偏好；有缓解时娱乐需要不再累积（[一日运行保真规格 1.2](../dev/SPEC-life-runtime.md#dayrun-fidelity-身体与需要-下限缓解与累积口径)） |

工作报酬按计时、计件或包干合同计算；实际投入充分仍须满足交付验收条件。
交换引擎使用验收结果，不组织验收过程；合同不额外乘质量分数，也不重复扣减身体效率已经影响的产出。
涉及身体资源时，只返回本次交换对应的输入或消耗；持续身体演化与体感更新由模拟引擎负责。
具体计算约束见[消费、生产与需求模型](../dev/SPEC-life-runtime.md#spec-life-runtime-消费生产与需求模型)和[资金与合同](../dev/SPEC-life-runtime.md#spec-life-runtime-资金与合同)。

**食品例子：** 购买时计算付款与取得数量，返回交付要求；进食时按实际吃掉的份量计算食品输入。
没有实际进食，就没有这部分食品消耗或能量输入。

<a name="exchange-engine-校验资源分录"></a>
### 校验资源分录

**目的：检查本次计算出的变化能否应用。** 输入是变化前的余额或数量，以及本次变化明细；
输出是符合约束的结果，或具体的失败原因。分录是一次资源增减的明细，校验通过不表示状态已经保存。

| 校验什么 | 必须满足什么 |
| --- | --- |
| 资源与单位 | 按已定义的资源和单位计算，不混用金额、份量和热量 |
| 归属与数量 | 资源归属明确，数量合法，同一项变化不重复计算 |
| 余额与边界 | 普通账户不能透支，库存不能为负，变化后的资源符合上下界 |
| 资金守恒 | 同种封闭资源的转出与转入对应，初始注资也须有来源 |
| 开放资源 | 增加和消耗各有原因，变化前后能够对应 |
| 转换 | 投入与产出明确，涉及的每种资源分别满足约束 |

初始资金的外部注资账户按规则允许为负，普通账户不适用这个例外。
校验针对本次交换；跨历史记录的重建、对账和完整性审计由记录引擎负责。

**食品例子：** 买方扣款应等于商家收款，吃掉的份量不能超过开吃份量；结束进食时未吃的开吃份量记为丢弃，不产生能量输入；
给予按 `from`、`to` 从本人手边转入对方持有，转出与转入数量对应。
一笔合法转账只能说明付款规则成立，不能证明食品已送达或已吃掉。

<a name="exchange-engine-返回规则结果"></a>
### 返回规则结果

**目的：把本次判断、计算与校验的结果交给模拟引擎。**
结果要清楚区分“允许执行”和“根据已发生事实算出的变化”，不能把预计产出描述为完成结果。
制作结果必须列明真实消耗、产物与数量；输入和输出的 `inventory_unit=item`，库存资源仍为 `inventory/item`。
暂停、取消或提前结束不制造半件产物。全部接口拒绝给出英文说明，`items[]` 每项包含
`path/written/error_code/allowed_values/expected/why/candidates`；`path` 从模型工具调用根开始，保留全部数组下标，
`why` 写参数、名称或世界前置条件的英文原因。不以笼统失败代替参数诊断，不采用旧 `index/field` 形状。
可照填候选只用完整 `{tool, arguments, note}` 调用。
`query_world(name, way, category, from, available_only, offset)` 读取同一冻结权限下的对象与报价事实；category 来自公开可调用索引，
`from` 与购买请求用同一个来源解析函数（地点显示名或渠道称呼，只匹配供给条目），`available_only` 只读取冻结观察里已求得的动作与工具
`available`，不重新求值交换条件，成功仍以受理时的重验为准；以 matches/total_count/next_offset 返回可遍历的每页结果，逐项不再附候选，
不触发交换求值副作用或呈现留痕。

| 结果内容 | 应表达什么 |
| --- | --- |
| 条件判定 | 当前动作或交换是否满足要求 |
| 变化明细 | 哪一方的什么资源应增加或减少多少，以及计算所依据的事实 |
| 履约条件 | 取得、使用、付款或交付还需满足什么条件 |
| 拒绝原因 | 哪个条件或资源约束不满足，不能用替代行动冒充成功 |

模拟引擎消费这些结果，负责执行、安排履约和更新状态。交换引擎没有独立的世界状态，
也不负责事件排队、时间推进或记录保存。

<a name="exchange-engine-食品交换的规则调用"></a>
#### 食品交换的规则调用

<a name="exchange-engine-分阶段验证与完成条件"></a>
### 分阶段验证与完成条件

```mermaid
flowchart LR
    D[规则一致<br/>同一交换使用同义定义] --> C[功能接通<br/>实际调用使用指定规则]
    C --> V[结果验证<br/>允许、拒绝与变化量符合规则]
```

| 验证功能 | 必须确认的结果 |
| --- | --- |
| 维护交换规则 | 新条目关联到可执行的规则；修改能定位受影响的引用；删除后无失效引用且同类其他条目的规则仍可用；新发布不修改已绑定的版本 |
| 查询适用规则 | 同一动作与目标使用指定规则；缺失资源、错误单位或交换双方不明确时不能继续求值 |
| 校验交换条件 | 余额不足、库存不足、未交付、无资格或报价失效时拒绝，并说明原因；能量不足不构成拒绝；距截止或剩余合同不足 60 秒不开工（`ACTIVITY_DURATION_INVALID`） |
| 计算投入产出 | 购买不计进食效果，进食按实际份量计算，报酬符合合同和验收条件，重复付款被拒绝；接触次数只在首次与从头重看时加一；不足一份按实际份量计算，结束进食丢弃的剩余与给予都不计摄入 |
| 校验资源分录 | 转入转出对应，数量与余额满足边界，开放资源的增加和消耗有依据 |
| 返回规则结果 | 明确区分条件判定、预计投入和实际变化；返回履约要求或拒绝原因，不自行改变世界 |

品类特性按冻结规格完成确定性与真实离线运行路径验证，证据以专项台账为准。
正式模型的长期运行验收仍见[验证规则](../VERIFICATION.md#verification-worldmock-验收标准)。
