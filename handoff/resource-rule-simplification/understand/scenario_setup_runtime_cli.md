## 5. What the proposal changes here

The proposal's requirements that land in this subsystem: (a) classification and exchange rules fixed in WorldMock, dataset supplies only names/summaries/numbers/bindings, old formats rejected; (b) random weighted connected map replaces the real map; (c) same-type stores share one menu, foods in three fixed-calorie classes bound to stores or `all`; (d) delivery reaches every registered location; (e) app catalog from the environment, restaurants and contents bound to apps, push notifications; (f) work = topic + target hours; (g) no compatibility layers; format switch covers published environment, scenarios, checkpoints, footprints and phone handoff. Smallest design that reuses existing mechanisms:

### 5.1 Scenario structure 6 -> 7 (`src/worldmock/life/scenario.py`)
- `LifeScenario.schema_version`, `RuntimeScenario.schema_version`: `Literal[6]` -> `Literal[7]` (REWRITE). Old structure rejected by the existing `extra=forbid`/Literal mechanism; no migration.
- DELETE fields: `map_dataset` (`MapDatasetReference`), `products[]` (`ProductReference`), `supplies[]` (`SupplyReference`), `contents[]` (`ContentItemConfig`, `CONTENT_KINDS`), `games[]` (`GameConfig`), `price_changes[]` (`PriceChangeConfig`), `product_releases[]` (`ProductReleaseConfig`), `recipe_output_bindings`, `phone_simulation_config` + `_sha256`, `catalog_version` (`CatalogVersionPin`) if the environment identity moves to a single environment manifest (see 5.2; otherwise keep as the pin of the new registry version), `tasks[]` as `WorkTaskConfig` (contract kind, pay, materials, oracle, skills), `messages[].related_task_id` and `attachment_sha256`, `AgentConfig.skill_levels`/`qualifications` (only consumed by tasks, supplies and location access; qualifications on locations go with the real map), `InventoryItemConfig`/`ProductConfig` runtime models.
- REWRITE: `tasks[]` -> `work_topics[]{topic_id, assignee_agent_id, topic, target_hours}` (proposal "工作主题: 标识、主题、目标工时; 由场景分配给人物; 沿用场景的工作地点和班次"). `assignee_agent_id` keeps the `agent:<id>`/`<id>` spelling; `required_location_id` is dropped in favour of `work_schedule.workplace_location_id` (open question 8.6 if a topic needs a place when `work_schedule` is null). `_check_catalog_references` shrinks to assignee existence; `_check_times` drops task windows; `runtime_tasks` and `RuntimeWorkTask` are deleted; `WorkAppointment` deleted.

## 8. Open questions the spec must decide

1. Environment identity shape: keep `catalog_version{major,minor}` as the scenario pin of the new registry (smallest change for `assemble_semantics`'s pin check) or replace it with one `environment_version` string in the registry manifest plus `content_sha256` and `map_sha256` bound into the run manifest? Either way the four category fields disappear from `category_identity`/`require_category_identity` (`run_identity.py`).
2. Where does the fixed-rule version live and how is it bound: a `RULES_VERSION` constant in code (changes `code_sha256` anyway) versus a package resource whose bytes are copied into the environment like `affordances.toml` (extends `_require_engine_rules`)? The proposal says "运行身份同时绑定引擎规则版本和环境内容摘要" (engine-evidence "未来可验证断言").
3. Map generation entry point: library-only (`generate_map(location_ids, seed, ...)` called by Dataset tools that already import WorldMock) or also a `worldmock environment generate-map` CLI row in `contracts-cli`? Decision table "地图是否全连通" (recommended: 全连通 via random spanning tree + extra edges) fixes the algorithm but not the entry point; loading and restore read the published graph only.
4. Scenario still selects `locations[]`? The proposal keeps "地点清单" in the catalog and the scenario keeps `interaction_menus_by_location_kind`/`home_location_id`; if the scenario selects a subset, `all` and same-type-menu checks must be evaluated on the registry (not the selection) and delivery "全地图可达" means every selected location. Recommend: keep `locations[]` selection, registry checks on the full registry, delivery to every selected location.
5. Work topics: catalog object (`work_topics.json`, scenario binds `topic_id -> agent`) as the proposal's five-catalog table implies, or scenario-only objects (`work_topics[]{topic_id, topic, target_hours, assignee_agent_id}`)? Scenario-only is smaller (no registry file, no reverse index) and matches "由场景分配给人物"; it changes the catalog count in `docs/dev/PROPOSAL...` "五类目录" to four.
6. Topic work place and payment: topics have no `required_location_id`; a person with `work_schedule: null` assigned a topic — allowed anywhere, or rejected at load (`check_work_schedules` extension)? Payroll stays as the only pay path (proposal: "工资复用已有独立工资预排事件").
7. Decision table "营业与供给": 不设库存、店铺全天服务 (recommended) deletes `opening_calendars`, `opening_exceptions`, the closing-warning wake reasons and `OpeningCalendar`; the alternative keeps fixed per-type opening hours as a WorldMock constant table (then `opening_hours.py` survives with a fixed table and the registry has no opening fields).
8. Decision table "做饭是否保留": deleting cooking removes `recipe_output_bindings`, `inventory_recipe.py`, ingredient class; keeping it as a fixed-duration lifestyle activity leaves `lifestyle/items.json` untouched. Affects `LifeScenario` fields and `_PRODUCT_USE_MODES`.
9. Decision table "session 的含义" (recommended: reuse stay/transit sessions): push eligibility state keyed by `SessionState.session_id`; needs a ruling on persistence (world state field on `AgentState`) and on whether a push received in transit survives arrival (the recommended option says no: "session 切换时直接清除其推送资格").
10. Decision table "推送频率": hourly 08:00–21:00 ticks compiled into `pending_events` per local day (how many ticks are created up-front for an 84-day run: ~14×84 per person; alternative: one rolling `push_tick` re-armed by the handler) — pick to keep `compile_schedule` deterministic and checkpoint-restorable without duplicates.
11. Decision table "外卖时间" and "食品常数": the fixed constants (prep time, delivery speed, fee, 200/100/600 kcal, 5/3/20 min) are registered in `EXPERIMENT.md#experiment-实验假设声明`; the spec must state whether they live in `src/worldmock/data/*.toml` (byte-bound) or Python constants.
12. Input-warning closed set after deletion (5 codes) and whether `validate`'s coverage targets still need `media_kinds` when the person no longer picks content; whether taste weights (`taste_weights` on `AgentState`, `_card_taste_weights`) are deleted or repurposed to app choice.
13. Stage identity: delete `work_review` only, or keep a second stage for the work-narration call at progress reports (the proposal: "同一段工作只在既有进度播报时生成描述" — generated by the person's own decision model inside the report, so no separate stage is the smallest answer).
14. Messages: keep scenario `messages[]` as plain mail (drop `related_task_id`, `attachment_sha256`), or delete entirely now that tasks are gone? Contact replies and `message_arrival` still need the `Message` model; recommend keep as plain mail.
15. TextWorld/games and the podcast/SRT corpus: the proposal's exit table removes them; the spec must say whether `textworld` leaves the dependency lock (bootstrap docs, `SPEC-shared-rules` x86_64/aarch64 clause) or stays because other code uses it (proposal: "通用库有其他现行用途时保留").
16. Dataset-dependent tests: with the real map gone, `tests/life/test_load_checks.py` and the Dataset-only storefront tests must be rewritten against the artificial environment (they then join the standard tier); decide whether `--environment-root` keeps its role for the new Dataset environment (yes per SPEC-environment-data-ownership) and what the full-tier environment is until the Dataset republishes.
