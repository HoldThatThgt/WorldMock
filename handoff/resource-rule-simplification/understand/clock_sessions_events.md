### 1.4 Control flow in one paragraph (current behaviour)

`LifeEnv.step(tick, t)` -> `engine.advance` -> `TimeAdvanceCoordinator.advance`: rejects if a round is open or anyone is ready; the target must equal `_next_epoch()` (min of `end_time`, `reminders.boundary_candidates` [next local midnight, untriggered plan reminders, awake errand reminders], `awake_duty_edge_times`, every `pending_events.due_at > now`, every `agent.next_decision_at > now`, every active activity's `planned_end_at` and `next_interaction_at`, every agent's predicted body boundary). It then flushes presentation, sets `current_time`, `same_moment.reset_same_moment`, `_advance_activities` (per agent: one `body_settlement` draft, then each activity -> `activity_progress`, end-of-sleep by reminder, arrival session switch), `_process_scheduled` (pops events with `due_at == target`, applies effects, writes `environment_event{kind=<ScheduledKind>, scheduled_id, ...}` with `source_kind="scenario"`, collects per-agent wake flags), `errands.settle`, then either `apply_engine_rhythm` or (local midnight) `settle_engine_rhythm` + `hold_body_settlements` so the decide segment runs in `decide_midnight_rhythm` after `plan_day`. The decide segment (`rhythm.decide_decision_rhythm`) builds `WakeSnapshot` per agent, evaluates reasons, marks messages read (awake only) and reminders triggered, writes `next_decision_at` (= now if offered, else `next_decision_candidates` or now+interval), `pending_wake_reasons`. The observation (`observe.py:249`) and `decision_started.data.wake_reasons` (`decision_start.py:35`) copy `pending_wake_reasons`. Same-second rounds are scheduled by `decision_coordinator._round_schedule` -> `same_moment.schedule_after_round` (never through `advance`).

## 5. What the proposal changes here

Guiding reuse: `pending_events` + `apply_scheduled_effect` for anything that happens "at a simulated instant", `WakeReason` + `_SCHEDULED_WAKE_FLAGS` for waking, `environment_event` with `visibility="agent"` + a progress-layer record for "the person sees it", `WorldState.sessions` + `current_session` for "same session", `WorldState.random_state` for deterministic draws, the checkpointed `WorldState` for restore idempotence. No new scheduler, timer, inbox or session type.

### 5.2 Content completion (proposal "娱乐选择 app，系统选择内容")

No new `ScheduledKind` and no new `WakeReason`. The app-use activity owns a "current content" and its end instant; content completion is an intra-activity boundary:
- The activity sets `next_interaction_at = min(now + remaining_seconds_of_current_content, planned_end_at)` on start/resume/content switch. `_next_epoch` already treats `next_interaction_at` as a clock boundary (`time_advance.py:484`).
- In `_apply_activity_effect` the app-use branch (replacing the WATCH branch `reveal_watch`) advances `content_progress[content_id].position_seconds`; when the content is complete it records the completion in `activity_progress.data` (content id, completion count) and, if `planned_end_at > now`, draws the next content (deterministic RNG from `random_state`, `activity_id`, draw index; pushed content takes precedence only at open, per the proposal), releases matching `app_pushes`, and sets the new `next_interaction_at`.
- `rhythm.decide_engine_rhythm` currently re-arms `next_interaction_at` through `schedule_feedback` for every non-game activity whose `next_interaction_at <= target`; because the effect already moved it into the future, the loop leaves it alone. If the effect leaves it `None` (nothing left to draw: empty app), the loop would re-arm it to `now + feedback_seconds`, which is harmless (silent boundary). Document this ordering (`_advance_activities` runs before the rhythm) in the spec.
- Completion is silent (no decision offered). The person is next asked at `planned_end` (activity end), `progress_report_due`, or any other reason. Open question 8.3 asks whether a completion should offer a decision; the proposal flowchart does not require one.
- DELETE in `time_advance._apply_activity_effect`: the WATCH branch (`reveal_watch`, `rules.cues`, `_dedupe_revealed_cues`), READ_MAIL branch if mail is removed, and the WORK branch (`reveal_work_progress`, `_record_material_reveal`, `work_material` evidence) per 5.4.

## 8. Open questions for the spec

8.1 **Session meaning** (proposal decision table "session 的含义": "复用地点／路途 session：复用现有上下文；长停留时推送资格也较长 | 新定义 app session"). Recommendation here: reuse (`sessions.current_session`), as 5.1 assumes. Consequence to state explicitly: a push at the arrival second is issued *after* `_switch_session_on_arrival` and therefore belongs to the new stay session for eligibility, while the progress layer attributes that commit to the transit session (`session_bounds`, `test_arrival_commit_belongs_wholly_to_the_transit_session`); the record will show in the road session's events but the pin applies at the destination. Accept, or exclude pushes from arrival seconds.

8.2 **Wake-reason members without a source** (`task_available`, `task_due_soon`, `work_review_result`, `location_hours_change` if hours go, `commitment_threatened` half): keep names "retained, no source" (precedent `activity_infeasible`, `discovery_result`; keeps `WAKE_REASON_NAMES` able to validate historical runs) or delete them under "旧格式直接拒绝". The frozen clause currently forbids deletion; the spec must choose and rewrite `spec-life-runtime-决策节律结算边界与唤醒条件分离` either way.

8.3 **Is `app_push` a decision opportunity, and is content completion one?** Proposal: push "进入人物可见上下文" and "复用既有调度与唤醒规则" -> recommended yes for push (awake only, like `message_arrival`), no for content completion (silent switch, the flowchart draws the next content without asking). Alternative: push only writes the record and waits for the next natural boundary (cheaper in model calls: up to 14 extra decisions per person per day).

8.4 **Push to a sleeping person**: issue and store (visible after waking, eligibility still bound to the session; wake filtered by the sleep whitelist) versus skip issuance while asleep. Recommended: issue (mirrors messages; no extra state). Also decide whether a push issued during sleep that is then followed by the agent waking in the same stay session should still pin (per the eligibility table it does).

8.5 **Push frequency** (decision table "推送频率": per person per hour at most one + per app per session at most one, versus per app per day). The compile-time hourly events assume the recommended option; the per-app-per-day option would instead need one event per app per day and a different eligibility key.

8.6 **DST and the hourly grid**: `clock_epoch`/`duty_edges` precedent is "skipped local times use the pre-jump offset, repeated times take the first occurrence"; fix the same rule for `_app_push_rows` (`fold=0`) and whether a skipped hour produces a push at all.

8.7 **Exact window edges**: pushes at 08:00 ≤ t ≤ 21:00 on the hour (14 per day) with "22:00 only limits new pushes"; confirm that a push due exactly at `start_at` is excluded (`start < due`, consistent with every compiled row) and that a run starting at 09:30 gets its first push at 10:00.

8.8 **`source_kind` and visibility of the push event**: `_process_scheduled` stamps every scheduled event `source_kind="scenario"`; a push is a system policy, not scenario material. Keep "scenario" for uniformity or use "environment" (the footprint closed set allows both).

8.9 **Deleted scheduled kinds and old checkpoints**: `ScheduledKind` is a StrEnum, so a version-10 checkpoint cannot contain the removed kinds anyway; confirm that the removal of `price_change`/`supply_quote_change`/`product_release` is tied to the "营业与供给" ruling ("无库存、店铺全天服务" recommended vs "按类型固定营业时间") and that `bill_due`, `payroll`, `calendar_flag`, `message_arrival`, `delivery_arrival`, `mail_arrival` (if mail stays) remain.

8.10 **Work hours accrual** (decision table "工作工时": actual seconds vs effective seconds): rhythm already records `activity_efficiency` on work `activity_progress`; the spec must say whether that field stays as a body fact (recommended) while completion uses `elapsed_seconds` only.

8.11 **Progress-layer record for a push that was not issued** (no eligible app): no record, system-visible event only (recommended), so the person never sees "nothing to push".

8.12 **Ledger handling**: whether the deleted task/quote-related `SourceMutation` rows in `tests/tool_interaction_acceptance.py` and the task evidence in `tests/time_and_energy_acceptance.py` are removed with their features (the proposal says "删除失去生产用途的...测试夹具"), and whether `tests/idle_fillers_acceptance.py` registered source texts (`rhythm::_wake_snapshot`, `time_advance::_next_epoch`) are preserved byte-for-byte when task inputs are removed from `_wake_snapshot`.
