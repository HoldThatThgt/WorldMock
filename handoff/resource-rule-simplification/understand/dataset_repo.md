Headline answer to the focus question: **the engine's complete-day and full-tier runs cannot be satisfied without a re-made dataset environment.** `scripts/run_tests.py --tier full --environment-root ../WorldMock-Dataset/environment/zhangjiang-baseline` is the documented full gate (`docs/dev/SPEC-environment-data-ownership.md`, `docs/CONTRACTS.md#contracts-环境数据归属合同`); `tests/integration/test_dayrun_complete_days.py` reads `multi-person.json` from `ENVIRONMENT_ROOT`, pins `random_seed` 20260105/20260106 and the Zhangjiang restaurant names `菜饭骨头汤` / `三十六道金牌煲仔饭`; `tests/life/test_purchase_channels.py` reads the published `supplies.json`. The artificial fixture `WM/tests/fixtures/environment/` (1 location `home`, 1 product `milk`, 0 supplies, 0 routes, 1 subtitle content, 0 tasks) only carries the external-lifecycle test. Because the proposal rejects old formats outright (no compatibility layer), *both* the artificial fixture and the Zhangjiang baseline (and the six `requests/*` environments if they are to stay runnable) must be re-issued in the new catalog format before any engine test can run; the complete-day test additionally needs same-type stores, apps and three food classes in whichever environment it is pointed at.

## 5. What the proposal changes here

Guiding rule from the proposal: Dataset supplies only names, summaries, synthetic numbers and bindings; WorldMock fixes classification, constants and exchange rules; old formats are rejected; no compatibility layers. The smallest correct design keeps the existing *mechanisms* (manifest + content hash identity, `safe_file`, `DataSource`, `load_manifest`, frozen-input bundles, export → phone → labelkit chain, `run_day` stages, atomic publish, `--environment-root`) and replaces the *catalog payload*.

### 5.1 Published environment: new object catalog (ADD) replacing the category/exchange payload (DELETE)
ADD a single environment snapshot `environment/<name>/catalog/` with one JSON per catalog (names are a proposal, to be fixed by the spec):
- `catalog/manifest.json`: `{format_version, environment_id, environment_version, rules_version (WorldMock fixed-rules version string), files{relative: sha256}, catalog_content_sha256}` — reuse `worldmock.categories.identity.refresh_manifest_identity`-style content digest (rename to environment identity).
- `catalog/apps.json`: `{apps[]{app_id, name}}` — the app catalog; "真实名称", no package names, no capability flags.
- `catalog/places.json`: `{places[]{place_id, name, place_type ∈ WorldMock enum (`home, office, restaurant, coffee_shop, convenience_store, supermarket, park, …` — the proposal suggests 餐馆/咖啡店/便利店/超市 as food store types), app_ids[] (restaurants/food stores only; empty = dine-in only)}}` — replaces `locations.json` (no coordinates, opening calendars, `business_kind`, `location_kinds`, `required_qualifications`, `brand`, `affordances`) and `supply-assumptions.json`/`category-assignment.json`/`<seed>/supplies.json`.
- `catalog/foods.json`: `{foods[]{food_id, name, food_class ∈ {snack, drink, meal} ("零食/饮品/正餐"), price_fen, stores: "all" | [place_id…], summary?}}` — replaces `objects.jsonl` food rows, `foods/expansion*.json`, `purchase-price-ranges.json`, `open-food-facts/*`, `meals/items.json`, `ingredients/items.json`, `off-foods.mapping.toml`. Registration validates: class valid, price > 0, store ids exist and are food-capable types, per-type all-or-nothing binding (proposal decision "同类店铺的食品绑定"), `all` expands only to food-capable types.
- `catalog/contents.json`: `{contents[]{content_id, name, content_type ∈ {article, image_text, short_video, long_video, live} ("文章/图文/短视频/长视频/实况"), summary, summary_source{kind real|synthetic, url?, notice}, duration_seconds (synthetic-marked), app_ids[] (≥1), series?{work, episode}}}` — replaces `movies/drama/novels/feed/jokes/podcasts/games/sintel/social` corpora and SRT timelines; one `contents.json`, no per-kind directories, no `timeline_path/timeline_sha256`, no `genre/language/age_rating`.

### 7.3 Cross-subsystem dependencies the spec must coordinate
1. **Registration validator in WorldMock** (resource engine subsystem): the single function the dataset `--check`, `dataset_preflight`, and `LifeEngine.create` all call; it must expose: place types enum, food classes + fixed kcal/eat-time table, content types enum, app binding checks, per-type all-or-nothing store binding, `all` expansion, graph generation `generate_map(place_ids, seed)` and `shortest_path_m(a, b)`.
2. **Engine event/activity payloads** (recording subsystem) that `simulate_phone.py` will project: `app_use` activity (`target_id=app_id`, `data{content_id, consumed_seconds, pushed}`), `app_push` environment event (`agent_id, app_id, content_id, summary, session_id`), order payload `app_id/place_id/food_id/receive_place_id`, `delivery_arrival.orders[].app_id`, work `progress_report` narration rows (`topic_id, worked_seconds, remaining_seconds, narration`).
3. **Scenario schema 7** (scenario/setup subsystem): fields in §5.3; `work_schedule` and `payrolls` retained verbatim; `messages[].related_task_id` disposition.
4. **Export manifest identity** (footprints subsystem): `frozen_run_manifest` fields consumed by `labelkit_input.py`, `audit_sources.py`, `verify_day_run.py`.
5. **Lifestyle corpus** (content subsystem): keeps `effects/location_kinds/time_window`; the three phone-scrolling fillers and `environment/idle-fillers.json` entries must be withdrawn in the same change as the `app_use` action, or the system layer will still advertise "刷B站" as a lifestyle activity.
6. **Package rule resources** (`worldmock.data` affordances/motivation/persona-mapping): decide whether the frozen copies stay in the environment (then `environment_rules.py` and `test_engine_package_resources.py` survive) or are replaced by `rules_version` in the manifest.
7. **LabelKit input contract** (`docs/CONTRACTS.md#contracts-labelkit-输入结构与窗口编码`): phone rows change shape; window builders in `src/worldmock/delivery/*` that treat `phone_event` records must be checked (they currently pass the payload through).

## 8. Open questions the spec must decide

1. **Same-type store binding** (proposal decision table "同类店铺的食品绑定": 精确绑定并校验同类一致 vs 按店铺类型填写绑定). Affects `foods.json.stores` shape (`[place_id]` vs `[place_type]`) and the validator error. Recommendation for the dataset side: accept `stores: "all" | [place_type…]` — it makes the author's intent explicit and the all-or-nothing check unnecessary; the proposal's recommended option (per-store ids + consistency check) is also implementable.
2. **Map connectivity** ("地图是否全连通"): the dataset only publishes what the engine generates; the spec must fix the generation rule (tree + k extra edges, length range) and the published `map.json` shape so `--check` can byte-compare it.
3. **Opening hours** ("营业与供给": 店铺全天服务 vs 按类型固定营业时间): if per-type hours are kept, they are a WorldMock constant table, not a dataset `opening_calendars` file — confirm the dataset emits nothing.
4. **Cooking** ("做饭是否保留"): deletion removes `ingredients/`, `recipe_output_bindings`, `test_cooking_chain.py`, `preflight_runtime.check_recipes`, `persona-targets.recipes`; keeping it as a fixed-duration lifestyle activity needs no dataset data.
5. **Opening stock at home** (`environment/home-pantry.json`, 7 servings): not mentioned by the proposal; decide whether `agents[].initial_inventory{home:{food_id: qty}}` survives (foods from `foods.json`), else delete pantry declarations and the 家的可供性 clause.
6. **Content identity for series** ("同名内容按作品与集数区分"): fix the fields (`series_title`, `episode`) and whether `long_video` episodes of a real drama are separate `content_id`s (proposal: 真实电视剧按集登记，电影按部登记).
7. **Summary provenance**: the proposal requires real summaries keep source info and synthetic ones be marked; decide the minimal `summary_source{kind, url?, retrieved_at?, notice}` (reuse `DataSource` with `kind ∈ fact|scenario`) and whether licences are still tracked per content (currently `corpora/manifest.json` entries carry `license`).
8. **App catalog scope**: does `apps.json` also host messaging/payment/navigation apps now encoded in `phone-simulation.json` (`amap`, `alipay`, `wechat`, `dingtalk`)? The proposal says "已有消息等行为使用同一 app 身份；本提案不另造社交系统" — spec must say whether contacts bind to an `app_id` in the scenario and whether payment/navigation sessions are dropped from the phone projection (they would otherwise need a config outside the catalog, which the proposal forbids).
9. **Per-persona environments vs one shared environment**: the current repo publishes one baseline plus six request overlays (catalog 5.6, own maps). Under "格式切换同时覆盖发布环境、场景…", decide whether `requests/*` become scenario-only (selecting places/apps from one shared environment) or each ships a full snapshot; this fixes whether `catalog_publish.py`'s overlay concept has any successor.
10. **Work topics and payroll**: `work_topics[]` per agent, `target_hours` per topic vs per window; whether `messages[].related_task_id` is deleted; whether the existing `payrolls[]` events stay exactly as is (proposal: yes).
11. **Phone projection ownership**: with app facts in the engine export, should `simulate_phone.py` survive at all, or should the engine export `phone.jsonl` directly (proposal: "手机导出直接读取实际动作中的 app、店铺和内容身份")? If the engine exports it, `simulate_phone.py` and the `phone` stage in `run_day.py` are deleted and `labelkit_input.py` reads the export artifact.
12. **Push window and session semantics** (decision rows "session 的含义", "推送频率"): dataset-side only needs the `app_push` event shape; but `tools/verify_day_run.py::technical_pause`/window coverage must treat push events as non-decision events.
13. **Food constants** ("食品常数"): the dataset never writes kcal/eat time; `persona-targets.body` and `scenario.body` remain the only numeric body inputs — confirm `resources.jsonl` body parameters (`maximum_energy_kcal`, `basal_kcal_per_hour`, MET table, efficiency curves, `work_efficiency_curve`) move to WorldMock constants or to scenario `body` (today they come from `tools/catalog-snapshot-legacy-scenario.json` via `resources.jsonl`).
14. **Content progress vs re-watch** ("内容进度与重看"): no dataset data either way, but "看完后排除" would require a per-app minimum content count at registration (the proposal's "空内容集合明确显示该 app 没有娱乐内容" suggests none).
15. **Which engine tests keep using `--environment-root`**: decide whether the new artificial fixture is rich enough to carry the complete-day test (two agents, restaurants, apps), making the published environment optional for the full tier, or whether the full tier keeps requiring the Dataset's re-made environment (today's rule).
