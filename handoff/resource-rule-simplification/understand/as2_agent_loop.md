Scope confirmed and extended beyond the hints: the "model call points" are (1) the LifeAgent ReAct loop (the only per-decision call, including the progress-report decision), (2) the independent background clients built on `IndependentModelClient` — work review (`work_review.py`/`work_review_runtime.py`), zero-hour plan (`day_planning.py` + `runtime.settle_pending_day_plans`), contact reply (`runtime.settle_pending_model_replies`) — and (3) the AS2 memory runtime calls (consolidation and bedtime reflection in `life_memory.py`/`life_reflection.py`). ## 5. What the proposal changes in this subsystem

Guiding facts: (i) the model is called at a progress report exactly as at any other decision — `progress_report_due` is a wake reason, the request is the ordinary 7-layer action request, and the model's answer is `report_status.items[].summary`, stored in `ActivityState.progress_note`/`note_history` by `with_note(anchor=True)` and recorded in `action_requested.data.request` (progress layer `tool_call.arguments`). (ii) Both fingerprints are computed, never pinned as literals; `tool_schema_sha256` moves whenever `REQUEST_MODELS`, `TOOL_DESCRIPTIONS`, field descriptions or `affordances.toml` bytes change, `prompt_sha256` whenever a system-layer rule or any `LAYER_SCHEMAS` entry changes. (iii) `stage_model_identity` is validated to be exactly `{action, work_review}` at five entry points, so removing work review is a manifest-format change that rejects old runs — consistent with "旧格式直接拒绝".

## 8. Open questions the spec must decide

1. Decision table 「工作工时」: "实际工作秒数（推荐）" vs "有效工作秒数". Code impact: `work.work_totals` returns both; the completion gate, `contract.remaining`, `objective_progress`, `settled_text` and VERIFICATION `workload.effective_work_seconds` must pick one. If actual seconds win, does `effective_work_seconds` stay as a body/efficiency fact in `ActivityState` and `activities.advance_activity` (it also feeds motivation `daily_effective_work_seconds` in `scenario.MotivationProfile`)?
2. Does `submit_work` disappear entirely (proposal: "删除…作品提交、独立语义验收、返工及验收后任务付款") or stay as a no-review completion signal? Recommendation here: delete; completion is system-side at target hours. If deleted, how does a topic end before target hours (deadline `due_at` kept? `TASK_EXPIRED`?), and do task notification mails (`related_task_id`, `WORK_AVAILABLE`) remain the way a topic becomes visible, or do topics come straight from the scenario assignment ("由场景分配给人物")?
3. `WakeReason.WORK_REVIEW_RESULT`: the frozen vocabulary says members are never deleted (only added via the version table). The spec must either rule a one-time deletion (consistent with "旧格式直接拒绝") or leave an unused member.
4. "人物只选 app 和使用时长" vs frozen "模型不填时长；进行中活动有 30 分钟播报，可随时结束" (SPEC-life-runtime 派生时长上限) and the `start_activity` schema that has no duration field. Recommendation: keep the system-derived duration (= remaining of the drawn content), which makes "一次 app 使用活动内，当前内容结束前不抽新内容" automatic; then "完整结束后若使用时长尚未耗尽，随机抽取下一条" has no case and should be dropped, or the spec adds an app-session duration constant.
5. Decision table 「session 的含义」: reuse place/transit session (recommended) — then `SessionState.pushed_app_ids` and `AgentState.app_pushes` are cleared in `sessions.open_stay`/`begin_transit`; the proposal's row "session 已结束仍未完成指定内容 → 推送的优先资格结束" needs the rule for a push issued while on the road (transit session is a session too; is a push allowed during driving when app use is excluded by claims?).
6. Decision table 「推送频率」 and the push wake: is `app_push` a wake reason (one decision opportunity, like `errand_reminder_due`, not in `SLEEP_ALLOWED_REASONS`)? If the person sleeps or is mid-activity, is the push still recorded (visible later in the progress layer) even though no decision is offered? The proposal says "不打断当前内容" and "不会用墙钟计时器唤醒模拟" but also "作为通知进入人物可见上下文".
7. Decision table 「内容进度与重看」: shared progress across apps + allow rewatch (recommended) keeps `AgentState.content_progress` keyed by content id; `exposure_count` semantics (relief 摊薄 per exposure, `_validate_watch` rule) — keep, drop, or redefine for the five categories?
8. Resource claims for `use_app`: does app use add `screen` (driving cannot use apps at all) or keep an audio-like exception for some category? The proposal removes podcasts; rule 8 text "开车时只能再听播客或和人说话" must be rewritten either way.
9. Replace `watch`+`play_game` with one `use_app` kind (recommended, and `spec-agent-interaction-游戏简化` "play_game 保留" is overridden) or keep `play_game` for games as a sixth content category? The proposal's five categories have no game.
10. Where does the previous narration enter the prompt at a progress report: progress layer `tool_call.arguments.items[].summary` already shows it within the session; after a session switch it is in `recall_task_summary` only (the `report_status` summary never enters `self_notes`). Is that enough, or should the work activity target `state` carry the last note (prompt schema change)?
11. Whether `progress_report_interval_seconds` stays a scenario parameter (frozen as "场景参数 1800") when the proposal fixes rules in WorldMock ("分类规则和交换规则在 WorldMock 系统端钉死" does not clearly cover rhythm parameters).
12. Content category constants (duration per category? "消费时长" is per item in the proposal) and whether `entertainment_relief_per_hour` becomes a per-category system constant (relief channel `content_rate` reads it per item today).
13. Identity: do `prompt_sha256`/`tool_schema_sha256` stay two separate fingerprints and does the manifest `stage_model_identity` get `schema_version` 3, or is the single `action` stage kept under the existing key with the validator tightened (recommended: tighten, no new key, old manifests rejected like `decision_statement`)?
14. `scripts/probe_deepseek_strict.py` and `tests/test_probe_deepseek_strict.py` build the real `conclude_activity` tool; unaffected unless control tools change — confirm the control tools stay as they are (the proposal does not touch `errands`/`memories`).
