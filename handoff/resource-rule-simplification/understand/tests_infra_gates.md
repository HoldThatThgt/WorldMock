# Subsystem map: test infrastructure, tiers, acceptance ledgers, mutation runner, engineering gates, baselines

Worktree read: `D:/code/WorldMock/.claude/worktrees/rrs` (read-only). Proposal read in full:
`docs/dev/PROPOSAL_2026-10-06_RESOURCE_AND_RULE_SIMPLIFICATION.md`; evidence read where it names tests
(`docs/dev/research/resource-rule-simplification/engine-evidence.md` §"App 直接登记…", §"外卖仍限制…",
§"已存在的成熟依赖与最小验证路径"; `dataset-evidence.md` and `industry-evidence.md` contain no test content).

Everything below is about *how the repository proves things*, not about the business behaviour itself. The
headline facts the spec author needs first:

1. **Feature acceptance is machine-registered in two layers**: `tests/fixtures/acceptance_requirements.json`
   (the frozen "what must be proven" per feature, extracted from the archived specs) + a Python ledger
   module per feature (`tests/<feature>_acceptance.py`) that maps each row to pytest node ids and, for three
   features, to `SourceMutation` records. A guard test (`tests/test_<feature>_acceptance.py`) fails if the
   two drift, if a node does not resolve to a collected, un-skipped test, if a deferral marker appears, or if
   a mutation survives. Every doc anchor named by a ledger must exist and carry a "substantive body"
   (`tests/fixtures/current-feature-owners.json` + `scripts/documentation_owners.py`).
2. **The proposal deletes behaviour that is pinned by 331 owner requirements, 147 byte-frozen mutations and
   roughly 160 ledger rows across five archived features.** The gates are deliberately built so that
   deleting a row, a test, a mutation or an owner anchor is *always* a red build until the ledger, the
   fixture JSON and the owning document are changed together. There is no "soft delete".
3. **The complete-day test and most engine tests do not run against the in-repo fixture.** The artificial
   environment under `tests/fixtures/environment/` has one location (`home`), no supplies, no routes and
   one subtitle content; the complete-day script hard-codes two Zhangjiang restaurants, "Space Habitat" and
   "张江居所", and ~40 other test files reference Dataset-only names. The committed coverage report
   (`docs/dev/coverage-report.json`, 6588 passed on macOS) was produced with
   `--environment-root ../WorldMock-Dataset/environment/zhangjiang-baseline`. The redesign therefore needs a
   **new artificial environment fixture with the new catalog shapes** *and* a re-published Dataset
   environment before the full tier can be green again.
4. **The style gate, import-graph gate, single-source gate and documentation gate impose hard structural
   constraints on every new module** (CJK docstring on every function incl. private, ≤50 lines, ≤5 params,
   ≤120 cols, ≤2000 lines/file; DAG with a registered allow-list for function-level imports; no duplicated
   function bodies or rule tables; no new definitions of named shared symbols outside their owner file;
   `path.py::Symbol` references in docs/comments must resolve; `<a name>` anchors unique repo-wide).

## 8. Open questions the spec must settle (with the proposal's decision-table item where applicable)

1. **Sixth feature vs. in-place rewrite of five.** Does the redesign register as a new feature key in `acceptance_requirements.json`/`current-feature-owners.json` (requires generalising `tests/test_current_feature_owners.py::OWNERS` set and `tests/test_layering_acceptance.py::FEATURES`/archive assertion), or does it rewrite the five archived ledgers' rows in place? The guards work either way, but the archive assertion (`docs/archive/<feature>/SPEC-<feature>.md` must exist and cite `2cf23011…`) only fits already-archived features. Recommendation: new key + guard generalisation; delete contradictory rows from the five.
2. **What happens to the 147-mutation byte proof.** `layering-mutations` says all 147 are written against current definitions; after deletion the count is lower. Options: (a) relax `test_original_mutation_generation_has_complete_byte_equivalence_evidence` to "registered ∩ baseline"; (b) rewrite `mutation-symbol-baseline.json` (forbidden by "保持原始字节"?). The spec must choose and amend `layering-mutations` + `docs/dev/implementation-status.md#implementation-status-layering-and-test-tiers` row "原有源码变异不丢失".
3. **Third complete-day baseline.** Freeze `tests/fixtures/dayrun-resource-rule-baseline.json` after two matching runs on the new artificial fixture (consistent with `layering-baseline`), or rely only on the live assertions (as the idle-fillers spec did)? If frozen, `tests/dayrun_baseline.py` stays byte-identical (its sha is inside both historical JSONs).
4. **One environment or two.** Should the new artificial fixture be rich enough to make the whole suite pass without `--environment-root` (the ~40 Dataset-name test files would be rewritten to fixture names), or does the suite stay Dataset-bound? Decision table item "外卖时间" (固定备餐＋图上配送时间 vs 全部固定送达时间) and "地图是否全连通" determine whether the fixture needs a far node and ≥2 edges per the generator; the fixture must embed the *published* graph (loader must not regenerate from seed: "加载和恢复直接读取固定图").
5. **Which deleted old-format rejection tests become ledger rows.** The proposal requires "旧格式拒绝" and "非法对象或旧规则字段直接报错"; the existing pattern is `tests/life/test_session_state.py::test_world_state_schema_version_N_is_rejected` + `test_run_with_version_N_world_state_is_rejected_on_open` + `tests/delivery/test_publication.py::test_delivery_gate_rejects_version_N_exports`. The spec should list the old shapes that must have an explicit rejection test (scenario 6, catalog 3.0, `map_dataset`, `supplies`, `exchange-rules.json`, `timeline_path`, `WorkTaskConfig`).
6. **Push-notification session evidence and its mutation set.** Decision items "session 的含义" and "推送频率" fix the semantics; the ledger needs rows with engine evidence (`engine_factory` + `mutate` + `tests/life/conftest.py::submit_round`) and mutations named in the spec's "源码变异必须覆盖" paragraph (the errands guard requires every sentence to be covered by ≥1 mutation once its stage is done). Note `REMOVED_SYMBOLS` already forbids the identifiers `session_name`, `current_sessions`, `_session_sentences`, `_terminal_sessions` anywhere in `src`/`custom` — new push/session code must avoid these names or the time-and-energy guard fails.
7. **Work-topic rows vs. work-schedule rows.** Decision item "工作工时" (实际 vs 有效秒数) chooses the accumulation rule; the spec must say which existing errands/idle rows (`工作合同边界`, `计划与义务`, T1–T20) survive verbatim and which `_WORK`/`_WORK_REVIEW` nodes are deleted, because `tests/time_and_energy_acceptance.py::_GREEN_BASELINE_TESTS` and `persona_prompt_acceptance.py::PROGRAM_ERRORS["恢复工作越过合同截止"]` cannot be partially emptied (empty entries fail `test_every_registered_node_resolves_to_a_collected_unskipped_test`).
8. **Cooking / recipe retirement** (decision item "做饭是否保留"): if cooking is deleted, delete `tool-interaction` rows `料理`, mutations `recipe_no_input_debit/recipe_no_output_credit`, `tests/fixtures/tool_interaction_habits.json` chains that cook, `tests/life/test_tool_interaction_recipe.py`, and the errands `完成依据` clause "未完成制作不算、产出算"; if kept as a timed activity, the habits fixture still needs new preconditions (no `inventory` dict keyed by product ids).
9. **Inventory/opening hours** (decision item "营业与供给"): `tests/life/test_storefront_schedule.py`, `tests/corpora/test_storefront_release.py` (stock, richness, price positions) and the `storefront_fixtures.supply_row` keys (`opening_status`, `current_stock`, `quote_status`) go either way; the fixture scenario needs `opening_calendars` only if hours are kept.
10. **TextWorld and external marker.** Retiring the game chain removes the only Linux-x86_64-only dependency; the spec must update `shared-rules-门禁可选部件与操作系统` (TextWorld acceptance mandatory) and decide whether Windows can then run `scripts/run_tests.py` tiers — this changes the platform-receipt requirement in the proposal's stage 4 ("跨平台收据").
11. **Version headers.** Four current specs carry "当前场景结构为 `6`…" in their file headers; `test_docs_carry_no_pending_markers_of_this_feature` forbids the words 待验收/待重验 in status cells; the spec should prescribe the exact header rewrite and the version-table row id (pattern `<date>-resource-rule-…`) so the documentation gate and the idle-fillers doc test (planned `tests/test_idle_fillers_docs.py`, not present in the tree) stay consistent.
12. **Owner anchors for deleted behaviour.** When a current section such as `docs/dev/SPEC-map-and-storefront.md#tool-interaction-地点供给和价格-类别准入与逐店商品集合` is rewritten to the shared-menu rule, should its anchor be kept (owner map unchanged, row text in `acceptance_requirements.json` rewritten) or retired (row deleted from JSON + owners)? `substantive_body` only requires non-navigational prose, so keeping anchors is cheaper; but `layering-consistency` forbids "两套同时有效的要求", so the JSON row text must be rewritten in the same commit either way.
